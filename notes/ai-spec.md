# ИИ, очередь приказов и главный цикл — полная спецификация с числами

Цель документа: реализовать шаг симуляции, ГСЧ, очередь приказов, планировщик ИИ, поведение
дикой природы и условия победы JW на любом языке, не заглядывая в дизассемблер.

Всё ниже сверено с образом `pwar.img` (база 0x10000), с портом `reimpl/js/port/orders_ai.js`
(сходится с эталоном-unicorn байт в байт) и эмпирически — см. §12 «Как это проверено»
(1 111 298 сверок, 0 расхождений).

Смещения полей юнита — от базы записи (GAME-LOGIC §4.1). Машинные копии всех таблиц —
`reimpl/data/ai_*.json`.

## 1. Время и счётчики

| адрес | тип | смысл |
|---|---|---|
| `0x46c` | u32 | таймер BIOS, 18.2 Гц (единственный источник реального времени) |
| `0x36d80` | u16 | таймер BIOS на предыдущем кадре |
| `0x31ab0` | u32 | тики BIOS с начала партии |
| `0x3033c` | u16 | обратный счётчик делителя скорости |
| `0x30098` | u16 | делитель скорости из меню, 1..5 |
| `0x31ab4` | **u32** | **номер игрового шага** — источник времени ГСЧ и всей периодичности |
| `0x31b66` | u16 | **независимый** счётчик mod 16 (см. ниже) |

**`0x31b66` — не `шаг & 15`.** Это отдельный счётчик, который инкрементится рядом со счётчиком
шагов (`inc word [0x31b66]; and word [0x31b66],0xf`) и **нигде не сбрасывается** — ни при старте
партии, ни при загрузке карты. Читается ровно в четырёх местах: обработчики людей (`0x18154`),
зверей (`0x184c8`), растений (`0x1860e`) и зданий (`0x18847`) — все они делают регенерацию
`0x18ab2` только при `[0x31b66] == 0`. Итог: **регенерация происходит раз в 16 шагов, но её фаза
относительно номера шага произвольна** и зависит от предыстории процесса. В реимплементации это
должен быть отдельный счётчик, а не `step % 16` (эмпирически: в разных трассах фаза 0, 4, 8, 9, 12
— см. §12).

Один игровой шаг = `0x30098` тиков BIOS. При делителе 1 — 18.2 шага/с. Все числа ниже — в шагах.

## 2. Порядок шага симуляции (`0x17e1c`)

```
tick():                                  # вызывается из главного цикла каждый кадр
  t = word[0x46c]
  if (word[0x36d80] == t) return         # тика BIOS не было — выходим
  dword[0x31ab0]++ ;  word[0x36d80] = t
  if (--word[0x3033c] != 0) goto render  # ещё не досчитали делитель скорости
  word[0x3033c] = word[0x30098]

  dword[0x31ab4]++                       # НОМЕР ШАГА
  word[0x31b66] = (word[0x31b66] + 1) & 0xf

  call 0x13f4c                           # A. очередь приказов
  call 0x15f86                           # B. суммы статов по слотам ИИ

  # C. проход по двусвязному списку живых записей (голова 0x31b6c, next +0x60)
  esi = dword[0x31b6c]
  while (esi != 0):
      next = dword[esi + 0x60]           # next читается ДО обработки!
      if (byte[esi+0x5b] & 1):           # запись помечена мёртвой
          call 0x18058(esi); esi = next; continue
      f43 = byte[esi+0x43]               # «оглушение»
      if (f43 == 0):        dispatch(esi); esi = next; continue
      if (f43 & 3):         byte[esi+0x43] = f43 - 1
      if ((byte[esi+0x43] & 0xfc) == 0): dispatch(esi); esi = next; continue
      if ((dword[0x31ab4] & 3) == 0): byte[esi+0x43] -= 4
      if (byte[esi+0x2b] == 0x6f): byte[esi+0x43] = 0; dispatch(esi); esi = next; continue
      esi = next                         # юнит полностью пропущен в этом шаге

  call 0x200fe                           # D. очередь звуковых заявок
  call 0x1ab4c                           # E. снаряды и эффекты
  call 0x1c340                           # F. бит «предмет» в BI
  call 0x15634                           # G. планировщик ИИ + медленные таймеры

render:  ...                             # рендер раз в тик BIOS, если [0x30346] != 1

dispatch(esi):                           # таблица 0x17fb8[тип]
    тип 0        -> 0x17fb4  (ret)
    типы 1..13   -> 0x18154  (люди и ручные динозавры)
    типы 14..23  -> 0x184c8  (дикие звери)
    типы 24..25  -> 0x18568  (ядовитые растения)
    типы 26..39  -> 0x186b3  (здания)
```

**Оглушение `+0x43`.** Младшие 2 бита — короткая пауза (убывают каждый шаг), старшие 6 бит —
длинная (убывают на 4 раз в 4 шага). Пока старшие биты не нулевые, юнит **вообще не
обрабатывается** — кроме случая «умирает» (`state == 0x6f`), когда счётчик принудительно
обнуляется. Флаг ставится извне: `|= 2` при выдаче приказа атаки на цель (см. §4.3).

Проверка конца партии **не входит в шаг** — она в главном цикле (`0x100fe`):
```
if (byte[0x30349] != 0 || (word[0x31ab4] & 0x1f) == 0)  call 0x17728
```
То есть при `(шаг & 31) == 0` она вызывается **на каждом кадре**, пока номер шага не сменится
(при делителе скорости > 1 — несколько раз за один шаг). Проверка идемпотентна, поэтому это
безопасно, но воспроизводить лучше буквально.

## 3. ГСЧ

### 3.1 Основной генератор `0x20469`

```
rand():                                  # результат в EDX
  N = dword[0x31b58]                     # «диапазон», задаётся вызывающим ПЕРЕД вызовом
  if (N == 0) return 0
  e = (dword[0x31b5c] + dword[0x31ab4]) mod 2^32     # состояние + НОМЕР ШАГА
  q = e / N ;  r = e mod N                          # 32-битное беззнаковое деление
  dword[0x31b5c] = (dword[0x31b5c] + q) mod 2^32
  dword[0x31b5c] ^= dword[0x393ac + (q >> 28)]      # (!) БАЙТОВОЕ смещение, не индекс
  dword[0x393a0]++                                  # счётчик вызовов (нигде не читается)
  return r
```

- `0x31b58` — не «seed», а **модуль текущего розыгрыша**: каждый вызывающий кладёт туда своё
  число прямо перед `call`. Значение сохраняется до следующего вызова.
- `0x31b5c` — состояние. Начальное значение в образе — **25**, `0x31b58` — **1**.
- К состоянию **прибавляется номер шага**, поэтому последовательность полностью
  детерминирована от `(состояние, шаг)` и «догоняет» себя при одинаковой истории.

**Таблица `0x393ac`** (32 байта; `q >> 28` — байтовое смещение 0..15, значения перекрываются):

выровненные dword'ы: `0x00394951 0x0012f861 0x0041f4fb 0x00317ee1 0x0098967c 0x001301d6 0x00595da1 0x007fca30`

| q>>28 | dword[0x393ac + i] | q>>28 | dword[0x393ac + i] |
|---|---|---|---|
| 0 | 0x00394951 | 8 | 0x0012f861 |
| 1 | 0x61003949 | 9 | 0xfb0012f8 |
| 2 | 0xf8610039 | 10 | 0xf4fb0012 |
| 3 | 0x12f86100 | 11 | 0x41f4fb00 |
| 4 | 0x0012f861 | 12 | 0x0041f4fb |
| 5 | 0xfb0012f8 | 13 | 0xe10041f4 |
| 6 | 0xf4fb0012 | 14 | 0x7ee10041 |
| 7 | 0x41f4fb00 | 15 | 0x317ee100 |

Практическое следствие: `q >> 28 != 0` возможно только когда `q ≥ 2^28`, то есть при
`N ≤ 15` (при `N = 20` уже `q < 2^28` всегда). При типичных розыгрышах `rand(20)`, `rand(50)`,
`rand(100)`, `rand(200)` **индекс всегда 0**, и состояние каждый раз xor'ится на `0x00394951`.

### 3.2 Вариант с таймером BIOS `0x204a6`

Тот же расчёт, но состояние `0x393a4` (старт 1), модуль `0x393a8` (старт 5), а вместо номера
шага прибавляется **таймер BIOS `[0x46c]`**; счётчик вызовов не инкрементится.

Это **единственный источник недетерминизма** в партии. Он используется ровно в двух местах:
- `0x15da1` (инициализация ИИ): `rand(4)` на каждый из 8 слотов — выбор строки таблицы врагов;
- `0x18e0b` (состояние отдыха 0x2x): `rand(13)` раз в 32 шага при `(+0x42 & 1) == 0`; результат
  **не используется** (мёртвый вызов, но состояние `0x393a4` он двигает).

### 3.3 Где ГСЧ реально вызывается

Замер по хукам на живой игре (2 миссии × 1000 шагов, 16 751 вызов):

| адрес возврата | функция | модуль | доля |
|---|---|---|---|
| `0x18ed6` | `0x18e89`, состояние 0x38: таймер простоя `rand(20)+5` | 20 | 86 % |
| `0x18efd` | там же: поворот на месте `rand(3)−1` | 3 | 4 % |
| `0x1731d` / `0x1733d` | `0x172c5`: случайная точка выпаса зверя | ширина/высота прямоугольника | 7 % |
| `0x196b7` | `0x19693`: при смерти `+0x4f = rand(0x36)` | 54 | 0.4 % |
| `0x1b4f6` | урон эффекта заклинания: `rand(15) + [0x30b92]` | 15 | |
| `0x1b3fd` | площадь эффекта: `rand(14)` → таблица `0x36fe0` | 14 | |
| `0x188f4` / `0x18902` | рассыпание еды при гибели склада | 64 / 70 | |
| `0x1a475` | `0x1a463`: «бросить погоню?» — `rand(SPD)` | SPD | |
| `0x1689f` / `0x168b3` | разброс точки телепорта ИИ: `rand(8)*4`, `rand(5)−2` | 8 / 5 | |
| `0x15b31` | `0x15b20`: здания или юниты первыми — `rand(50)` | 50 | |
| `0x1575c` | `0x1572f`: подкрепление или порог — `rand(100)` | 100 | |
| `0x13fa8`… | случайный артефакт — **только в сетевой игре** | 10000, 15, mapH, mapW | 0 |

**Где ГСЧ не используется вообще:** в бою (расчёт урона детерминирован), в поиске пути, в
движении, в производстве зданий, в выборе цели атаки `0x15c07`/`0x15ca1`.

## 4. Очередь приказов

### 4.1 Формат и жизненный цикл

Записи по 10 байт, буфер от `0x33c88`, «конец» — указатель `0x33c7c`:

| смещение | тип | смысл |
|---|---|---|
| +0 | u8 | источник = `[0x333c0]` (маркер игрока; 0 в одиночной игре, 0xff — записи соперника) |
| +1 | u8 | код приказа |
| +2 | u16 | индекс записи юнита-адресата |
| +4 | u16 | цель (индекс записи юнита) |
| +6 | u16 | X (пиксели) |
| +8 | u16 | Y (пиксели) |

`0x14895` — добавить запись (в сетевой игре ещё считает 16-битную контрольную сумму в `0x33c86`).

```
0x13f4c (начало шага):
  dword[0x33c7c] = 0x33c88                      # очередь очищается КАЖДЫЙ шаг
  call 0x1419e                                  # разложить «ожидающий клик-приказ» UI в очередь
  if (byte[0x31b69] != 0):                      # сетевая игра
      обмен очередями (0x14942) + раз в 32 шага случайный артефакт (см. ниже)
  end = dword[0x33c7c]
  if (byte[0x333c0] != 0):                      # у соперника: сначала чужие, потом свои
      for c in [0x33c88, end) step 10: if (byte[c] == 0xff) apply(c)
      for c in [0x33c88, end) step 10: if (byte[c] != 0xff) apply(c)
  else:                                         # одиночная игра / первый игрок
      for c in [0x33c88, end) step 10: if (byte[c] != 0xff) apply(c)
      for c in [0x33c88, end) step 10: if (byte[c] == 0xff) apply(c)

apply(c):                                       # положить ОТЛОЖЕННЫЙ приказ в юнит
  esi = u16[c+2]
  if (byte[esi+0x46] == 0x6f) return            # уже приказано умереть
  st = byte[esi+0x2b];  if (st == 0x6f || st == 0x60) return
  byte[esi+0x46] = byte[c+1]                    # код
  dword[esi+0x47] = u16[c+4]                    # цель
  u16[esi+0x4b] = u16[c+6];  u16[esi+0x4d] = u16[c+8]   # точка
```

**Случайный артефакт** (`0x13f85`) находится ВНУТРИ сетевой ветки и в одиночной игре
**не выполняется** (в GAME-LOGIC §3.4 это описано неточно). Условия: `(шаг & 0x1f) == 0`,
`[0x3c53f] != 0`, `rand(10000) ≤ 50` (51/10000); предмет `15 + rand(15)`, клетка
`(rand(mapW), rand(mapH))`.

**Раздача UI-приказа** (`0x1419e`): в цикле снимается «ожидающий клик» (`0x14854`:
код `[0x31acc]`, цель `[0x31ad0]`, X `[0x31ad4]`, Y `[0x31ad8]`, после снятия `[0x31acc] = 0xff`)
и вызывается обработчик:
```
if (код < 0x80):  handler = dword[0x141f8 + (код>>4)*4] ;  edi = код >> 4
else:             ecx = код;  cl -= 0xa0;  handler = dword[0x14218 + ecx*4]
```
Проверки границ у второй таблицы нет; она фактически содержит 20 записей (коды 0xa0..0xb3).

### 4.2 Применение отложенного приказа — только на ровном тайле

В обработчике людей/динозавров `0x18154`:
```
if (word[0x31b66] == 0) call 0x18ab2(1)                    # регенерация
if (byte[+0x46] != 0xff && (byte[+0x2f] & 0x1f) == 0 && (byte[+0x31] & 0x1f) == 0):
     al = byte[+0x46]
     if (al == 0x6f && (state == 0x6f || state == 0x60)) return
     switch (al >> 4) по таблице 0x18268:
        0, 3..0xd -> 0x181d7   # state = al; +0x33 = цель; +0x37/+0x39 = точка; +0x46 = 0xff
        1, 2      -> 0x18211   # то же + word[+0x4f] = 0
        0xe       -> al == 0xe0 ? 0x181d7 : (+0x46 = 0xff; call 0x19bbe — команда меню сразу)
        0xf       -> ничего (0xff и прочие 0xf* игнорируются)
call 0x163e4                                                # реакции/магия/задачи ИИ
диспетчер состояния (0x182a8 по state>>4, либо 0x182c8 для state >= 0x80)
```
Обработчик зверей `0x184c8` делает то же, но **без** проверки кода 0x6f и без таблицы:
код всегда просто переписывается в состояние, а перед этим вызывается `0x172c5` (§8).

Важно: `+0x2b` получает **сам код приказа**, и уже диспетчер состояния в том же шаге переводит
его дальше. Наблюдаемое отображение (из трасс, §12):

| код | состояние на следующем шаге | смысл |
|---|---|---|
| 0x0f | 0x00 | идти в точку (0x1db94 → 0x00) |
| 0x1f | 0x11 | атаковать цель — подход |
| 0x33 | 0x31 | атака из охраны — подход |
| 0x37 | 0x36 | вернуться на пост |
| 0x3f | 0x38 | охрана/простой |
| 0x44 | 0x42 | подобрать/охотиться в клетке |
| 0x6f | 0x60 | умереть → труп |
| 0xa0..0xae | 0x80..0x8e | заклинание (код − 0x20) |

### 4.3 Полный список кодов приказов

Коды < 0x80 — таблица `0x141f8` по `код >> 4`:

| код>>4 | обработчик | что делает |
|---|---|---|
| 0 (0x0f) | `0x14398` | «идти» всем выделенным **с построением** (см. ниже) |
| 1 (0x1f) | `0x145cd` | атаковать юнит `esi`: всем выделенным, кроме самой цели; цели `+0x43 \|= 2` |
| 2 (0x2f) | `0x14621` | всем выделенным без проверок (отдых) |
| 3 (0x3f) | `0x14621` | всем выделенным без проверок (охрана) |
| 4 (0x4c) | `0x14642` | только «текущему» юниту `[0x31adc]`, если он не в 0x4x с той же точкой |
| 5 (0x51+n) | `0x14673` | «текущему» юниту, цель `esi`, цели `+0x43 \|= 2` |
| 6 | `0x1468c` | ret (не используется) |
| 7 | `0x1468d` | «текущему» юниту, цель `esi` |

Коды ≥ 0x80 — таблица `0x14218` по `код − 0xa0` (низкий байт, без проверки границ):

| код | обработчик | что делает |
|---|---|---|
| 0xa0..0xa4 | `0x1469a` | заклинание на цель, кастует `[0x31adc]`; допуск через `0x14873(код−0x98)` |
| 0xa5 | ret | — |
| 0xa6..0xa8 | `0x146c5` | заклинание на цель **всеми выделенными** |
| 0xa9 | `0x1469a` | заклинание на цель одним юнитом |
| 0xaa | ret | — |
| 0xab | `0x1469a` | |
| 0xac | `0x146c5` | |
| 0xad | `0x146fa` | заклинание в точку курсора `[0x31ae8]/[0x31aec]` |
| 0xae | `0x146c5` | |
| 0xaf | ret | — |
| 0xb0, 0xb1 | `0x1472c` | заклинание на самого себя (`esi = edi = [0x31adc]`, `+0x43 \|= 2`) |
| 0xb2 | `0x146c5` | телепорт (в точку) |
| 0xb3 | ret | — |

**Построение группы (`0x14398`).** Считает число выделенных `[0x33be0]` и габарит
(`0x33be8..0x33bee`), выравнивает по 32, `ax = ширина`, `bx = высота`.
Если `[0x44792] == 1 || [0x4479e] == 1` (зажат модификатор) **или** `выделено ≥ (ax*bx/1024)/2` —
вся группа **сдвигается целиком**, сохраняя взаимное расположение (центр габарита переносится в
точку клика, координаты клампятся в карту). Иначе строится сетка: число колонок = первый индекс
`k` в таблице `0x33c0c` (28 записей u32), для которого `[0x33c0c + k*4] ≥ выделено`, плюс 1;
юниты раскладываются по ячейкам 32×32 от угла `(клик − (кол/2)*32)`. Приказ не выдаётся юниту,
который уже стоит в состоянии 0 с той же целью.

### 4.4 Приказы, которые движок ставит сам (мимо очереди)

| функция | код | цель / точка |
|---|---|---|
| `0x19f43` | 0x0f | цель = 0, точка = (dx, bx) |
| `0x19f63` | 0x1f | цель = edi; **X берётся у цели, Y — у себя** (баг, §11) |
| `0x19fbf` | 0x1f | цель = 0, точка = (dx, bx) — «идти» у ИИ и зверей |
| `0x19fdf` | 0x33 | цель = edi, точка = своя; если цель уже мертва — вместо этого `0x1a34c` |
| `0x1a34c` | 0x3f | — (охрана/простой) |
| `0x1a354` | 0x37 | — (вернуться на пост `+0x44/+0x45`) |
| `0x1a35c` | 0x51+n | перенос предмета из слота n |
| `0x1a379` | al | заклинание на цель edi |
| `0x1a393` | al | заклинание в точку (X,Y выравниваются по 32) |
| `0x172c5`/`0x16612` | 0x44 | подобрать предмет в найденной клетке |

## 5. Суммы статов `0x15f86` (каждый шаг)

Обнуляются шесть массивов u16[8] и заново считаются по всему списку живых:

```
for a in (0x32b8c, 0x32b9c, 0x32bac, 0x32b3c, 0x32b4c, 0x32b5c): a[0..7] = 0
for u in список живых:
    if (u[+0x08] == 0) continue                 # (!) юниты без роли НЕ считаются
    if (u[+0x5b] & 1) continue
    slot = u[+0x05]; if (slot >= 8) continue
    type = u[+0x04]; if (type >= 0x1a) continue # здания не считаются
    grp = (u[+0x08] == 1) ? 3 : 0               # 3 = оборона, 0 = все остальные роли
    A[grp+0][slot] += u[+0x0c] + u[+0x0d]       # HPmax + MAG
    A[grp+1][slot] += u[+0x0f] + u[+0x10]       # ATK + DEF
    edi = dword[0x30dd8 + slot*4] + dword[0x30dfc + type*4]      # блок статистики игрока
    A[grp+2][slot] += byte[edi] + byte[edi+2] + byte[edi+4] + byte[edi+6]   # 4 потолка статов
A = [0x32b8c, 0x32b9c, 0x32bac, 0x32b3c, 0x32b4c, 0x32b5c]
```

`0x32bac` (сумма потолков по не-оборонным юнитам) — это **потолок для порога атаки** (§6.3).

## 6. Планировщик ИИ `0x15634`

### 6.1 Диспетчер и периодичность

```
0x15634:
  if ((byte[0x31ab4] & 0x1f) == 0):                     # каждые 32 шага
      call 0x13f48                                      # = ret (заглушка)
      if ((byte[0x31ab4] & 0x7f) == 0):                 # каждые 128 шагов
          call 0x1c370                                  # гниение предметов на земле
          if ((word[0x31ab4] & 0x1fff) == 0):           # каждые 8192 шага
              call 0x15a0a                              # «отвязка застрявших»
      slot = (byte[0x31ab4] >> 5) & 7 ;  dword[0x36680] = slot
      call dword[0x156b4 + byte[0x32aec+slot]*4]        # МАКРО-состояние слота
  if ((byte[0x31ab4] & 0x0f) != 0) return               # каждые 16 шагов
  slot = (byte[0x31ab4] & 0x70) >> 4 ;  dword[0x36680] = slot
  if (byte[0x32aec+slot] == 0) return
  jmp dword[0x156d0 + byte[0x32aec+slot]*4]             # МИКРО-задачи слота
```

- **макро**: раз в 32 шага, слот `(шаг>>5) & 7` → каждый слот раз в **256 шагов**;
- **микро**: раз в 16 шагов, слот `(шаг>>4) & 7` → каждый слот раз в **128 шагов**;
- макро-обработчики состояний 1, 4, 5 в конце **прыгают на 0x156a5** (тело микро-ветки) и
  выполняют микро-задачи для СВОЕГО слота, после чего управление возвращается в `0x15634`,
  и микро-ветка отрабатывает ещё раз — уже для слота `(шаг>>4) & 7`. То есть на шагах,
  кратных 32, микро-задачи выполняются **дважды, для двух разных слотов**.
  Важно: `0x156a5` перечитывает `0x32aec[slot]` **после** того, как макро-обработчик изменил
  состояние. Поэтому `0x157ab` (состояние 5) сначала ставит состояние 1 и дальше дёргает
  микро-обработчик состояния **1** (`0x157b7`), а не `0x157d6`; `0x157d6` достижим только на
  «чисто микро» шагах, пока слот ещё в состоянии 5. Так же `0x156ed` после перехода в 4
  дёргает `0x157c6`.

Таблицы обработчиков (индекс = состояние ИИ `0x32aec[slot]`):

| состояние | макро `0x156b4` | микро `0x156d0` |
|---|---|---|
| 0 | `0x156ec` ret | `0x157b6` ret |
| 1 | `0x156ed` накопление | `0x157b7` = оборона `0x15885` + атака `0x1580e` |
| 2 | `0x1572d` ret | `0x157c4` ret |
| 3 | `0x1572e` ret | `0x157c5` ret |
| 4 | `0x1572f` атака идёт | `0x157c6` = оборона `0x15885` + атака `0x158fb` |
| 5 | `0x157ab` → состояние 1 | `0x157d6` = оборона `0x15982` + атака `0x158fb` |
| 6 | `0x157b5` ret | `0x157e0` ret |
| **7** | **чтение за таблицу**: `dword[0x156b4+28] = dword[0x156d0] = 0x157b6` → ret (безвредно) | **чтение за таблицу**: `dword[0x156d0+28] = dword[0x156ec]` = байты кода `0x048b66c3` → **вылет** |

Обе таблицы лежат вплотную и содержат ровно по 7 записей (0..6), поэтому состояние 7 в
макро-ветке безвредно, а в микро-ветке роняет игру (проверено, §13). Функция `0x157e1`
(`esi = slot; 0x15a3e`) — **мёртвый код**: на неё не ссылается ни одна таблица
(микро-запись для 6 — это `0x157e0`, то есть `ret`). Ранняя заметка «состояние 7 → только
отвязка» неверна.

Установка состояния: `0x157e9` → 0, `0x157f1` → 1, `0x157fb` → 4 (и `0x32b7c[slot] = 0`).
Состояния 2, 3, 6 в игре не встречаются; 5 и 7 могут прийти только из карты (секция GI).

### 6.2 Инициализация `0x15da1` (один раз при старте партии)

```
dword[0x393a8] = 4
for slot = 0..7:
    byte[0x32afc+slot] = 1
    d = rand_bios()                                  # 0x204a6, диапазон 4 -> 0..3
    byte[0x32af4+slot] = d
    byte[0x32b04+slot] = byte[0x32d2c + slot*32 + byte[0x32afc+slot] + d*8]
    if (byte[0x32aec+slot] == 0) continue            # слот не под ИИ
    byte[0x32aec+slot] = 1
    e = slot*10
    byte[0x32bcc+e] = 8; byte[0x32bcd+e] = 0         # задача обороны: «искать»
    byte[0x32c1c+e] = 8; byte[0x32c1d+e] = 0         # задача атаки:   «искать»
    u16[0x32c7c+slot*2] += 200
    if (сложность != 2) { += 80 ; if (сложность != 1) += 80 }
```

Порог атаки = **база из карты + 200/280/360** (hard / normal / easy). На hard ИИ атакует раньше.
Пример (миссия 10, племя 3): база `[50, 50, 50, 50, 215, 205, 50, 453]`, на normal у ИИ-слотов
0, 4, 5, 6, 7 порог становится `330, 495, 485, 330, 733`.

**Таблица врагов `0x32d2c`** — 8 слотов × 4 варианта × 8 байт, заполняется из карты (секция GI);
в образе EXE нули. Индексация: `0x32d2c[slot*32 + idx + variant*8]`, `idx` стартует с 1 и
циклится 1..7 (запись с `idx = 0` никогда не используется). Смена врага `0x15e45`:
```
idx = byte[0x32afc+slot] + 1;  if (idx >= 8) idx = 1;  byte[0x32afc+slot] = idx
byte[0x32b04+slot] = byte[0x32d2c + slot*32 + idx + byte[0x32af4+slot]*8]
```
Пересчёт после смены владельцев (`0x17dd4`) идёт от `variant*8` и ищет первого врага, у которого
владелец слота отличается от своего (не более 8 попыток).

### 6.3 Макро-состояния

**Состояние 1 — накопление (`0x156ed`, раз в 256 шагов на слот):**
```
sila = u16[0x32b8c+slot*2] + u16[0x32b9c+slot*2]        # HPmax+MAG + ATK+DEF по не-оборонным
if (sila < u16[0x32c7c+slot*2]) return                  # ещё не набрали
0x157fb: состояние = 4, u16[0x32b7c+slot*2] = 0         # обнулить счётчик потерь ударных
u16[0x32bbc+slot*2] = 0                                 # обнулить счётчик «дошли»
0x15b20(задача атаки, slot)                             # выбрать цель
переход в микро-ветку
```

Порог в картах выставлен так, что **разрыв «текущая сила → порог» на старте почти всегда
ровно 330** (замер на normal): m3 484→814, m6 1475→1805, m8 784→1114, m9 2050→2380,
m10 165→495, m11 611→941, m12 900→1230 (исключение — m4: 736→1250). База в карте =
стартовая сила + 50, а `0x15da1` добавляет 280 (normal). Поднять сумму `0x32b8c + 0x32b9c`
можно только двумя способами: создать новый ударный юнит (`0x15e82`, но это делается **уже
внутри** состояния 4) или вырастить статы существующих через XP (`0x1f475`). Поэтому
**в партии без боевых потерь ИИ никогда не переходит в атаку** — проверено прогоном на
9000 шагов (§13, секция F): все пять ИИ-слотов миссии 10 всё время остаются в состоянии 1.
Атака запускается только после того, как юниты ИИ повоюют и вырастут в статах.

**Состояние 4 — атака идёт (`0x1572f`):**
```
if (u16[0x32b7c+slot*2] < u16[0x32b1c+slot*2]) return   # ещё не все ударные погибли
r = rand(100)
if (r < 50):  0x15e82                                   # создать ещё одного ударного
else:         u16[0x32c7c+slot*2] += 100
              if (порог > u16[0x32bac+slot*2]) порог = u16[0x32bac+slot*2]
0x157f1: состояние = 1
u16[0x32bbc+slot*2] = 0
0x15ac6(slot, роль 2)                                   # всем ударным — идти на точку спавна
переход в микро-ветку
```
То есть волна заканчивается, когда **число погибших ударных юнитов с начала волны догоняет
общее число когда-либо созданных ударных** (`0x32b1c` никогда не обнуляется).

**Состояние 5 (`0x157ab`)** — просто перевод в 1 и переход в микро-ветку.

### 6.4 Счётчики группы

| счётчик | где инкрементится |
|---|---|
| `0x32b0c[slot]` зачислено в оборону | `0x15f1c` (мобилизация) |
| `0x32b2c[slot]` погибло из обороны | `0x196f6` (истёк труп) при `+0x08 == 1` |
| `0x32b1c[slot]` создано ударных | `0x15e82` |
| `0x32b7c[slot]` погибло ударных | `0x196f6` при `+0x08 != 0 && != 1` |
| `0x32b6c[slot]` дошло из обороны | `0x18b6a` (прибытие) при `+0x08 == 1` |
| `0x32bbc[slot]` дошло ударных | `0x18b6a` при `+0x08 != 0 && != 1` |

Прибытие (`0x18b6a`) дополнительно инкрементирует байт `+0x52`; при переполнении (было 0xff)
юнит переводится в состояние `0x2f` (отдых).

**Мобилизация обороны `0x15f1c(owner, slot)`:** идёт по списку живых, берёт юнитов этого слота
и владельца, у которых `(state & 0x60) != 0`, `тип ≤ 13` и `+0x08 == 0`; ставит `+0x08 = 1` и
`0x32b0c[slot]++`, пока `0x32b0c − 0x32b2c ≥ 5` (то есть **добирает группу обороны до 5 живых**).

**Создание ударного `0x15e82`:** находит первый живой юнит слота с `+0x08 == 2`, создаёт
(`0x1caf0`) юнит того же типа на его точке спавна `+0x59/+0x5a`, ставит `+0x08 = 2`,
`+0x5b = 3` (мёртв + «не освобождать запись»), `word[+0x4f] = 0` и снимает отпечаток с сетки.
`0x32b1c[slot]++`. Смысл: запись сразу помечается мёртвой, поэтому в следующем шаге ею займётся
`0x18058` → `0x1ced8` и **закажет такого же юнита в своём здании**. Если ударных нет вообще —
не делает ничего.

**Возврат на точку спавна `0x15ac6(slot, роль)`:** всем живым юнитам слота с этой ролью —
приказ 0x0f в точку `(+0x59 << 5, +0x5a << 5)`.

### 6.5 Задачи (10 байт)

`0x32bcc + slot*10` — оборона, `0x32c1c + slot*10` — атака (`0x36684[slot] = slot*10`).

| смещение | смысл |
|---|---|
| +0 | состояние: 0 «ждать пополнения», 4 «есть цель», 8 «искать», 0xc «пауза» |
| +1 | счётчик пауз (ставится 3) |
| +2 | u32, индекс записи юнита-цели |
| +6 | u16 X (выровнен по 32) |
| +8 | u16 Y (**не** выровнен, см. §11) |

Автомат (`0x1580e` атака из состояния 1, `0x15885` оборона, `0x158fb` атака из состояний 4/5,
`0x15982` оборона из состояния 5) — раз в 16 шагов:

```
состояние 0:  if (создано > дошло) return               # атака: 0x32b1c > 0x32bbc
                                                        # оборона: 0x32b0c > 0x32b6c
              -> 8
состояние 4:  ничего (цель есть)
состояние 8:  поиск цели (варианты ниже); нашли -> 4 и записать цель; нет -> 0xc, счётчик 3
состояние 0xc: if (--счётчик == 0) -> 8
```

**Поиск, вариант «около базы» (`0x15c07`, используется в `0x1580e` и `0x15885`):**
идёт по списку живых и берёт первого юнита, у которого:
- не мёртв, состояние не в 0x60..0x6f;
- координаты внутри прямоугольника базы `0x32f4c + slot*8` (u16 x1,y1,x2,y2 — из карты);
- владелец **не** равен владельцу нашего слота;
- `HP < ax` и `ATK+DEF < dx`, где для атаки `ax = 0x32b8c[slot]`, `dx = 0x32b9c[slot]`,
  для обороны `ax = 0x32b3c[slot]`, `dx = 0x32b4c[slot]`.

То есть **ИИ нападает только на цель, заведомо слабее суммарной силы своей группы**.

**Поиск, вариант «по владельцу-цели» (`0x158fb`, `0x15982`):**
```
0x15ca1(владелец-цель al, роль edi):     # роль 2 для атаки, 1 для обороны
    если владелец нашего слота == al -> неудача
    ebp = первая запись списка с +0x05 == слот, +0x06 == наш владелец,
          (!) +0x5b == 1 (ровно 1 — «мёртвая, но сохранённая») и +0x08 == роль
    если такой нет -> неудача
    для каждого живого юнита владельца al:
        d = min(|ebp.X − X|, |ebp.Y − Y|)              # (!) МИНИМУМ модулей, не чебышёв
        if (word[0x36a00] < d): word[0x36a00] = d; dword[0x369fc] = юнит
    если [0x369fc] == 0 -> неудача, иначе вернуть [0x369fc]
если нашли -> задача 4 с этой целью
иначе если владелец-цель == свой владелец -> сменить врага (0x15e45)
иначе если у владельца-цели есть хоть один живой юнит (0x15d79) -> сменить врага (0x15e45)
иначе -> задача 4 с найденным в 0x15d79 юнитом
```
Две особенности: расстояние — **минимум** модулей разностей по осям (не чебышёвская метрика),
а `0x36a00`/`0x369fc` **не инициализируются** в функции. «Максимум» копится через всю партию,
и после первого срабатывания возвращается одна и та же (возможно, уже мёртвая) запись.
Опорный юнит группы ищется по условию `+0x5b == 1`, то есть это **не живой** юнит, а запись,
помеченная мёртвой и оставленная для перезаказа (такие создаёт `0x15e82`).

**Выбор цели при старте волны (`0x15b20`):**
```
[0x36a02] = 1;  r = rand(50)
если r < 25 -> сначала цикл по ЗДАНИЯМ (тип >= 0x1a) владельца-цели, потом по ЮНИТАМ
иначе       -> сначала по ЮНИТАМ, потом (если не нашли) по ЗДАНИЯМ
нашли:  задача[0] = 4, задача[+2] = юнит, задача[+6] = X & 0xffe0, задача[+8] = Y
не нашли ни там ни там: задача[0] = 0xc, задача[1] = 3
```
**Оба цикла содержат ошибку `je` вместо `jne`** (§11): проверяется только первая запись списка.

### 6.6 Отвязка застрявших (`0x15a0a`, раз в 8192 шага)

```
for slot = 7..0:
    if (byte[0x32ae4+slot] == byte[0x31b64]) continue    # слот человека
    st = byte[0x32aec+slot];  if (st == 0 || st == 5) continue
    0x15a3e(slot)

0x15a3e(slot):  для всех живых юнитов этого слота и владельца, у которых
    состояние не 0x60/0x6f, роль +0x08 == 0, тип < 0x18 и тип != 4,
    состояние в диапазоне 0x36..0x3f:
        word[+0x44] = word[+0x59]        # пост := точка спавна
        0x1a354                          # приказ 0x37 «вернуться на пост»
```

## 7. Поведение отдельного юнита ИИ (`0x163e4` → `0x16598`)

`0x163e4` вызывается каждый шаг перед диспетчером состояния:
```
if ((dword[0x31ab4] & 3) == 0 && тип в 5..8):            # раз в 4 шага, только маги
    тотем = [0x11, 0x1d, 0x13, 0x14][тип-5]
    если тотем лежит в слотах +0x24..+0x26 и мана < MAG -> мана++
switch (состояние >> 4):
    1 -> 0x16531   # в движении/бою: лечение и атакующая магия
    2 -> 0x16508   # отдых: если HP и мана полные -> 0x1a34c (приказ 0x3f)
    3 -> 0x16598   # охрана/простой/задачи ИИ
    иначе ничего
```

`0x16598`:
```
if (состояние < 0x36) -> 0x16531
if (byte[0x32aec + владелец] == 0) -> 0x16612            # владелец не ИИ: автосбор
edi = dword[0x36684 + слот*4]                            # = слот*10

```

Таблица `0x165d0` по роли `+0x08`:

| роль | обработчик | смысл |
|---|---|---|
| 0 | `0x16612` | свободен → автосбор предметов при простое |
| 1 | `0x165ec` | оборона базы: взять задачу `0x32bcc + слот*10` |
| 2 | `0x165ff` | ударная группа: взять задачу `0x32c1c + слот*10` |
| 3 | `0x1664a` | (см. §11 — попадает в обработчик задачи **без базового смещения**) |
| 4 | `0x1669f` | то же — «сопровождение» из заметок; реально ветка битая |
| 5, 6 | `0x16612` | как свободный |
| 7 | мусор `0x2bcc9f8a` | недостижимо (роли > 4 движок не ставит) |

Дальше — переход по состоянию задачи (таблица `0x165dc`, **байтовое** смещение `bl`):

| состояние задачи | обработчик | что делает юнит |
|---|---|---|
| 0 | `0x1664a` | стоит, если `\|задача.X − X\| ≤ 160` **и** `\|задача.Y − Y\| ≤ 160`; иначе приказ 0x0f в точку задачи (`+0x4b/+0x4d` = задача.X/Y, без выравнивания). Есть мёртвая проверка `состояние ≤ 0x0f → выход` |
| 4 | `0x1669f` | если цель задачи жива и не в 0x6x → `0x19fbf` (приказ 0x1f) в её клетку (X,Y &= ~31); иначе задача → 0xc со счётчиком **2** |
| 8, 0xc | `0x16612` | автосбор при простое |

`0x16612` (и его копия внутри `0x172c5` для зверей):
```
if (byte[+0x50] < 0x0e) return                           # счётчик безделья < 14
0x170f6  # спиральное сканирование колец на нужные предметы/еду
if (нашли): +0x46 = 0x44; +0x4b = tx*32; +0x4d = ty*32
+0x50 = 0
```

Счётчик безделья `+0x50` увеличивается на 1 каждый раз, когда в состоянии 0x38 истекает
таймер простоя (§8), то есть примерно раз в 5..24 шага. Порог 14 достигается за ~14 циклов
простоя ≈ 200 шагов.

## 8. Простой, охрана и автореакция

Состояние **0x3f** (`0x18e89`): запомнить пост `+0x44 = X>>5`, `+0x45 = Y>>5`,
перейти в **0x38**, `+0x2c = 1`, `+0x50 = 0`.

Состояние **0x38** — «стоим на посту»:
```
if (--byte[+0x2c] != 0):
    если тип == 0x0b (летающий) — обновить кадр; выйти
цель = 0x1a526(esi)                                      # кольца радиуса (SPD>>5)+1
if (цель != 0): 0x19fdf -> приказ 0x33 (атака из охраны); выйти
if (тип == 0x0b):  dl = 0x10                             # летающие: фиксированные 16 шагов
else:              dl = rand(20) + 5                     # 5..24 шага
byte[+0x2c] = dl ;  byte[+0x50]++                        # счётчик безделья
if (dl == 0x18):                                         # ровно 24 — вероятность 1/20
    d = DIR + (rand(3) − 1)                              # поворот на месте на ±1 октант
    if (d >= 9) DIR = 1 ; else if (d == 0) DIR = 8 ; else DIR = d
обновить кадр стойки
```

**Кого юнит замечает (`0x1a526` / `0x1a531`).** Обход клеток спиральной таблицы `0x305d0`
вокруг поста `+0x44/+0x45`; число клеток `0x3058c[ring]`, где `ring = (SPD>>5)+1` для `0x1a526`
и явный аргумент для `0x1a531`. Занятость клетки: `BI & 0xfc` → владелец+1 наземного,
иначе `MO & 0xf0` → владелец+1 летающего. Найденную запись даёт `0x1a692`. Фильтры:
```
если состояние цели == 0x60 -> пропустить
если владелец цели == свой владелец:
    если состояние цели 0x10 или 0x30 -> взять ЕЁ цель (+0x33), если та не в 0x60 -> вернуть
    иначе пропустить                                   # «прийти на помощь союзнику»
иначе (чужой):
    если свой владелец >= 8            -> вернуть      # дикие звери бьют всё
    если byte[0x32aec + свой владелец] >= 1 -> вернуть # юниты ИИ бьют всё, включая здания
    если тип цели < 0x1a               -> вернуть      # человек: только мобильные цели
    иначе пропустить                                   # человек не атакует здания автоматически
```
Обратите внимание: здесь `0x32aec` индексируется **владельцем**, а везде ещё — слотом (§11).

**Погоня и отказ от неё.** В состояниях 0x31/0x11 после каждого пройденного тайла:
```
0x1a463(цель.X & ~31, цель.Y & ~31):
    [0x31b58] = SPD ;  r = rand()
    if (r < 16) вернуть «цель в поле зрения»            # при SPD < 16 — всегда
    иначе искать клетку цели среди 0x3058c[SPD>>4] клеток спирали вокруг СЕБЯ
если «не в поле зрения» -> 0x1a354 (приказ 0x37, вернуться на пост)
```

**Дикие звери «передумывают» (`0x18ca0`).** В состояниях 0x1x, когда цель есть, но
`0x1a051` говорит «ещё не дошли», для типов **14..23**:
```
[0x31b58] = 200 ;  r = rand()
if (r == 100) -> 0x1a34c  (бросить цель, приказ 0x3f)
```
Ровно **1/200 за шаг** — и только у диких зверей.

## 9. Дикая природа

### 9.1 Решение зверя `0x172c5` (вызывается из `0x184c8` на ровном тайле)

```
if (byte[+0x50] < 0x0e) return                          # счётчик безделья < 14
if ((состояние & 0xf0) != 0x40):                        # не занят добычей
    0x170f6                                             # искать еду/предмет по кольцам
    if (нашли): +0x46 = 0x44; +0x4b = tx*32; +0x4d = ty*32
    else:
        [0x31b58] = (byte[+0x58] − byte[+0x56]) & 0xff  # высота прямоугольника выпаса
        ty = byte[+0x56] + rand()
        [0x31b58] = (byte[+0x57] − byte[+0x55]) & 0xff  # ширина
        tx = byte[+0x55] + rand()
        if (0x1e609(tx*32, ty*32) == «проходимо»):  0x19fbf -> приказ 0x1f в эту точку
byte[+0x50] = 0
```
Прямоугольник выпаса `+0x55..+0x58` = (x1, y1, x2, y2) в тайлах, задаётся при создании зверя
(`0x1caf0`) как ±3 тайла от точки спавна с клампом по карте; типичные диапазоны розыгрыша — 6..7.

Приказ 0x1f с целью 0 переводит зверя в состояние 0x1f → 0x11 → он идёт к точке «боевой»
машиной состояний с нулевой целью.

### 9.2 Респавн (`0x18058` → `0x1cfcb`)

`0x18058` вызывается каждый шаг для каждой записи с `+0x5b & 1`:
```
владелец = byte[+0x06]
if (владелец != 8 && byte[0x32aec + владелец] == 0) return   # трупы человека не «тикают»
if (word[+0x4f] == 0xffff) return                            # заказ уже оформлен
порог = u16[0x36d82 + тип*2] + (тип в 14..23 ? dword[0x33358 + тип*4] : 0)
word[+0x4f]++
if (word[+0x4f] < порог) return
switch (тип) по таблице 0x180b4:
    0            -> ничего
    1..13, 26..39 -> 0x1ced8   (перезаказ копии в своём здании)
    14..23        -> 0x1cfcb   (респавн дикого зверя)
    24..25        -> 0x1d12e   (отрастание растения на месте)
```

`+0x4f` при смерти (`0x19693`, переход 0x6f → 0x60) инициализируется как **`rand(54)`**,
поэтому одинаковые звери не возрождаются синхронно.

`dword[0x33358 + тип*4]` — счётчик убитых особей этого вида: **чем больше зверей вида убито,
тем дольше они возрождаются** (порог растёт на 1 шаг за каждую убитую особь).

## 10. Производство ИИ (`0x1ced8`)

```
дом = cs:0x1cfa3[тип]                       # 1..3 -> 27, 4 -> 26, 5..13 -> 31..39, 26..39 -> 26
edi = первое живое здание типа «дом» того же СЛОТА, у которого (byte[+0x50] & 7) == 0
if (edi == 0) { word[+0x4f] = 0; return }   # нет свободного здания — ждать ещё цикл
цена = byte[0x30eac + (дом−26)*128 + тип*4] * byte[0x315ac + (дом−26)*32 + тип]
if (dword[0x31c28 + владелец*4] >= цена):
    word[+0x4f] = 0xffff                    # эта запись больше не тикает
    byte[edi+0x2b] = 0x7f                   # зданию — приказ производства
    dword[edi+0x33] = тип
    dword[edi+0x23] = esi                   # заказчик = сам погибший (реинкарнация в ту же запись)
    return
# еды не хватает
ax = 0x32b0c[слот] − 0x32b2c[слот]          # живых в группе обороны
if (0x32b0c[слот] >= 0x32b2c[слот] && ax >= 5) { word[+0x4f] = 0; return }
0x15f1c(владелец, слот)                     # добрать оборону до 5
word[+0x4f] = 0
```

Итог: **ИИ воспроизводит армию строго по образцу стартовой расстановки** — каждый погибший
юнит периодически заказывает копию самого себя в «своём» здании, а ударная группа растёт
копированием собственных юнитов (`0x15e82`). Никакого «выбора состава» у ИИ нет.

Здания (типы 26..39) тоже проходят через `0x1ced8` (дом = 26 Sanctuary), то есть **разрушенное
здание ИИ автоматически перезаказывается** через 540/1080 шагов, если хватает еды.

### Сложность

`0x303b2 = [15, 0, 15]` — применяется **один раз при старте миссии** (`0x1545a`), не в ИИ:
- **easy (0):** каждому юниту человека (тип < 26) `HPmax, HP, ATK, DEF, MAG, мана, SPD += 15`
  и пересчёт доступных заклинаний; каждому чужому юниту `HPmax, ATK, DEF −= 10` (пол 5),
  `MAG −= 10` (пол 0), `HP = HPmax`, `мана = MAG`; человеку `+5000` еды.
- **normal (1):** ничего.
- **hard (2):** каждому чужому юниту (тип < 26) все семь статов `+= 15`;
  каждому слоту, чей владелец не человек, `+20000` еды.

Ещё две таблицы сложности (контратака при ударе по зданию ИИ, `0x1e758`):
`0x369e4 = [0, 400, 1000]` — добавка к оценке силы врага, `0x369f0 = [0, 3, 6]` — добавка к
числу врагов. И порог атаки `+200/+280/+360` (§6.2).

## 11. Условия победы и поражения (`0x17728`)

```
0x17728:
  if (byte[0x31b69] == 1) ... сетевая ветка ...
  if (0x17d5f() == «нет живых юнитов у человека») { byte[0x30349] = 1; return CF=1 }
  0x17861: ebx = byte[0x31abb]*8 + word[0x31b64]      # миссия (0-based) * 8 + владелец-человек
           call dword[0x36a60 + ebx*4]
```
Код исхода `[0x30349]`: **1 — поражение, 2 — победа** (4 — соперник вышел, 5 — рассинхрон).
Проверка — на шагах, кратных 32 (и на каждом кадре, пока `[0x30349] != 0`).

Вспомогательные счётчики:
- `0x17879(владелец)` — обнуляет `0x36be0..0x36bef` и считает **достроенные** здания владельца
  по типу в `byte[0x36bc6 + тип]` (то есть `0x36be0` = тип 26 … `0x36bed` = тип 39);
  здания с `+0x50 & 2` (в процессе) не считаются;
- `0x178e7` — живые юниты по владельцу в `u16[0x36bf0 + владелец*2]`;
- `0x17947` — живые юниты по типу в `u16[0x36c04 + тип*2]`.

Гибель любого — поражение; оба во владении человека — победа.

**Миссии 9–12** (`0x17d28`): у всех слотов, чей владелец `0x32ae4[slot]` не равен владельцу
человека, `u16[0x36bf0 + slot*2] == 0`. Внимание: индексация счётчика `0x36bf0` идёт по
**номеру слота**, а сам счётчик заполнен по **владельцу** (§11).

## 12. Странности оригинала, которые нужно повторить

1. **`0x31b66` — независимый счётчик mod 16**, не `шаг & 15`; регенерация раз в 16 шагов
   имеет произвольную фазу (§1). В трассах наблюдались фазы 0, 4, 8, 9 и 12.
2. **Индекс таблицы ГСЧ `0x393ac` — байтовое смещение**, а не индекс dword: 16 значений
   перекрываются (§3.1). При `N ≥ 16` индекс всегда 0.
3. **`0x15b20` (выбор цели волны): `je` вместо `jne`.** Обе петли по списку юнитов
   заканчиваются `mov edx,[edx+0x60]; or edx,edx; je <начало петли>` — то есть петля
   продолжается, только если `next == 0`. Реально проверяется **лишь первая запись списка**;
   если её `next == 0`, обход уходит на запись пула 0 и зацикливается. Порт воспроизводит
   буквально, добавив предохранитель. Практически: цель волны почти всегда «не найдена»,
   задача уходит в 0xc/3, и настоящее целеуказание делает `0x158fb` (`0x15ca1`).
4. **`shl ax, 0xe0` в `0x15b20`**: счётчик сдвига `0xe0 & 0x1f = 0`, сдвига нет. Поэтому X цели
   в задаче выровнен по 32, а Y — сырой.
5. **`0x19f63` (приказ 0x1f «атаковать юнит»)**: `dx` берётся из X **цели**, а `bx` — из Y
   **самого атакующего**. Точка приказа получается «косой».
6. **`0x36a00`/`0x369fc` в `0x15ca1` не сбрасываются**: «максимум расстояния» копится через всю
   партию, и после первого срабатывания функция почти всегда возвращает одну и ту же цель.
   Там же «расстояние» — `min(|dx|, |dy|)`, а опорный юнит группы ищется по `+0x5b == 1`
   (мёртвая сохранённая запись), а не среди живых.
7. **`0x1a526` индексирует `0x32aec` владельцем**, а не слотом (везде ещё — слотом). В миссиях,
   где номер владельца ≠ номеру слота, это меняет фильтр «атаковать здания».
8. **`0x17d28` (миссии 9–12) индексирует `0x36bf0` слотом**, а счётчик заполнен по владельцу.
9. **`0x17bfa` (миссия 5) не проверяет слоты `+0x21..+0x23`** — артефакт в «поясе» победу
   не засчитывает.
10. **Роли 3 и 4 в `0x165d0`** ведут прямо в обработчики состояния задачи (`0x1664a`, `0x1669f`)
    с `edi = слот*10` **без прибавления базы задачи** (`0x32bcc`/`0x32c1c`) — то есть читают
    память по адресам 0..70. Движок такие роли не выставляет, ветка мёртвая; переносить не нужно,
    но и «чинить» её нельзя.
11. **`0x1419e` не проверяет границу второй таблицы** (`0x14218`): коды 0x80..0x9f дадут
    индексы 0xe0..0xff и уход далеко за таблицу. Легальный диапазон — 0xa0..0xb3.
12. **Случайный артефакт на карте — только в сетевой игре** (блок внутри `if [0x31b69] != 0`).
13. **`0x13f48`, вызываемая раз в 32 шага, — это `ret`** (пустая заглушка).
14. **`+0x52` (счётчик прибытий) переполняется**: после 256 прибытий юнит сам уходит в отдых 0x2f.
15. **Отдых у здорового юнита длится один шаг**: приказ 0x2f → состояние 0x2f, но `0x163e4` →
    `0x16508` сразу видит полные HP и ману и ставит приказ 0x3f.
16. **Счётчик убитых `0x33358[тип]` удлиняет респавн зверей** — вид постепенно «вымирает»
    (порог растёт на 1 шаг за каждую убитую особь).
17. **`0x1572f`**: волна кончается по числу **погибших** ударных (`0x32b7c ≥ 0x32b1c`), а
    `0x32b1c` никогда не обнуляется — значит, каждая следующая волна должна «потерять» всё
    больше юнитов, чтобы завершиться.
18. **Проверка победы вызывается из главного цикла на каждом кадре**, пока `(шаг & 31) == 0`
    или установлен код исхода — при делителе скорости > 1 это несколько вызовов на один шаг.
19. **Состояние ИИ 7 роняет игру.** Таблицы `0x156b4` и `0x156d0` лежат вплотную и содержат по
    7 записей (индексы 0..6). При `0x32aec[slot] == 7` макро-ветка читает `dword[0x156d0]`
    (= `0x157b6`, `ret` — безвредно), а микро-ветка — `dword[0x156ec]`, то есть **байты кода**
    `0x048b66c3`, и прыгает туда. Проверено: эмулятор падает на `UC_ERR_FETCH_UNMAPPED`.
    Функция `0x157e1` («esi = slot; отвязка») — мёртвый код, на неё нет ни одной ссылки.
20. **`0x157ab` (состояние 5) не выполняет `0x157d6`**: он сначала ставит состояние 1, а
    `0x156a5` перечитывает состояние заново и уходит в `0x157b7`. `0x157d6` работает только
    на «чисто микро» шагах, пока слот ещё в состоянии 5.
21. **ИИ не нападает в мирной партии.** Разрыв «сила → порог» на старте карт ровно 330,
    а сила растёт только через XP или через ударные юниты, которые создаются уже внутри
    состояния 4. За 9000 шагов без боёв ни один ИИ-слот не перешёл в атаку.

## 13. Как это проверено

`tools/spec_check_ai.py` — независимая реализация формул этого документа на Python; запуск из
`reimpl/`:

```
python3 ../tools/spec_check_ai.py --steps=1000 --long=9000 \
    traces/m0_t0 traces/m0_t0_orders traces/m1_t1 traces/m2_t0 traces/m3_t5 traces/m5_t0 \
    traces/m9_t3 traces/long_m1_t1 traces/long_m2_t0 traces/long_m5_t0 traces/long_m9_t3
```

Результат: **совпало 1 111 298, не совпало 0 → СПЕЦИФИКАЦИЯ ПОДТВЕРЖДЕНА.**

Что именно проверяется:

- **A. ГСЧ, чистая функция.** 2030 случайных троек `(состояние, модуль, шаг)` для `0x20469`
  и 500 для `0x204a6` подаются в эталон (unicorn) через прямой вызов функции; результат
  (EDX и новое состояние) сравнивается с формулой §3. Специально включены случаи
  `q >> 28 = 1..15`, покрывающие все 16 байтовых смещений таблицы `0x393ac`. **0 расхождений.**
- **B. ГСЧ в живой игре.** Хуки на входе и на всех `ret` обеих функций во время настоящих
  1000 шагов миссий 3 (`m2_t0`) и 10 (`m9_t3`): **16 751 вызов, 0 расхождений**. Попутно
  собраны гистограммы мест вызова и модулей — таблица в §3.3 построена по ним.
- **C. Периодичность.** По номерам шагов, на которых сработали хуки: `0x13f4c`, `0x15f86`,
  `0x15634` — ровно каждый шаг; `0x1c370` — ровно на 128, 256, 384…; `0x156ed`/`0x1572f` —
  только на кратных 32; `0x1580e`/`0x15885` — только на кратных 16; `0x17728` — только на
  кратных 32; `0x15a0a` за 1000 шагов не вызывалась (её период 8192).
- **D. Трассы** (11 трасс, `steps.bin`, 600 записей по 96 байт на шаг). Список живых
  восстанавливается по `+0x5c/+0x60` (голова `0x31b6c` в трассу не пишется), поэтому
  «мусорные» записи пула не мешают:
  - приказ применяется **только** когда `X & 0x1f == 0 && Y & 0x1f == 0` — 3943 применения,
    0 нарушений; 226 случаев, когда юнит был вне тайла и приказ сохранился до следующего шага;
  - `+0x2c` в состоянии 0x38 убывает ровно на 1 за шаг — 874 029 переходов;
  - при истечении таймера новый равен `rand(20)+5 ∈ [5,24]` (у летающих 0x10), и `+0x50`
    растёт ровно на 1 — 67 167 событий; отдельно учтён случай «нашли цель» (`+0x46 = 0x33`);
  - зверь с `+0x50 ≥ 14` на ровном тайле обнуляет счётчик — 2736 событий;
  - `+0x4f` мёртвой записи растёт не более чем на 1 за шаг — 139 048 переходов;
  - регенерация `+1 HP` (кроме отдыха 0x2x и лечения в состояниях ≥ 0x80) укладывается
    ровно в одну фазу mod 16 — по трассам фазы 0, 4, 8, 9, 12 (см. странность №1).
- **F. Длинный прогон и форсированные сценарии** (`--long[=N]`, по умолчанию 9000 шагов,
  миссия 10 / племя Masai). Файл трассы не пишется: 10 000 шагов × 57 632 байта — это 550 МБ,
  а всё нужное снимается хуками прямо в памяти эмулятора; прогон занимает ~90 с и 0 байт диска.
  - `0x15a0a` вызвана **ровно один раз, на шаге 8192**, и ни на каком другом;
  - `0x15a3e` вызвана ровно 5 раз — по одному на каждый ИИ-слот (0, 4, 5, 6, 7), слот человека
    и слоты с состоянием 0/5 пропущены;
  - на этом же шаге **33 юнита** ИИ в состояниях 0x36..0x3f с ролью 0 получили `+0x46 = 0x37`
    и `word[+0x44] = word[+0x59]` (пост := точка спавна) — 33 совпадения, 0 нарушений;
  - естественных переходов состояний ИИ за 9000 шагов **не произошло**: все 5 слотов всё время
    в состоянии 1 (причина — §6.3, разрыв до порога 330);
  - поэтому цикл волны проверен форсированно (миссия 3, слот 1, порог занижен до 1):
    1 → 4 с `0x32b7c = 0`, `0x32bbc = 0`, одним вызовом `0x15b20` и заполненной задачей атаки;
    затем при `0x32b7c := 0x32b1c` — переход 4 → 1 с веткой «порог += 100» (1 → 101 при
    потолке `0x32bac` = 2164) и приказом 0x0f на точку спавна всем трём ударным юнитам;
  - состояние 5: на «чисто микро» шаге отработал `0x157d6`, затем макро `0x157ab` перевёл слот
    в 1 (см. странность №20);
  - состояние 7: эмулятор падает на `UC_ERR_FETCH_UNMAPPED` — подтверждение странности №19.
- **E. Отложенный приказ ждёт тайла.** Отдельный сценарий на эталоне: юниту даётся приказ идти,
  затем посреди тайла — приказ 0x2f. Приказ висит в `+0x46` все 6 шагов до границы тайла и
  снимается ровно на первом шаге после выравнивания (состояние становится 0x20).

Дополнительно всё поведение покрыто штатной сверкой порта:
`node js/test/fntest.mjs cases/e_*` (63 кейса) и `node js/test/compare.mjs traces/m2_t0`
(300/300 шагов при активном ИИ).

**Что осталось без эмпирического подтверждения:** мёртвые ветки ролей 3/4 (`0x165d0`), сетевые
ветки `0x13f4c`/`0x1419e`/`0x14942` и спавн случайных артефактов (требуют второй машины по
COM-порту). Эти места описаны по дизассемблеру и по порту `orders_ai.js`.
Переход ИИ 1 → 4 → 1 и состояния 5/7 подтверждены форсированными сценариями (секция F), а не
естественным ходом партии: в мирной партии ИИ до порога атаки не дорастает (§6.3).
