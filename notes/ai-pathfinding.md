# Jurassic War — ИИ компьютерного игрока, поиск целей и движение

Источник: `out/decomp_named.c` (Ghidra) + дизассемблирование capstone участков, которые Ghidra не оформила в функции (0x15634–0x15a0a, 0x18154–0x18ab2). Адреса — образ `pwar.img`, база 0x10000. Поля юнита — смещения от `0xe4400 + ESI` (ESI = индекс записи).

## 1. Игроки и слоты

- До **8 слотов** (0..7). У юнита два байта: `U_PLAYER_IDX5` (+05) = слот, `U_OWNER` (+06) = «владелец/команда». Владелец **8** = дикие животные (нейтралы). `DAT_00032ae4[slot]` = владелец слота. Владелец человека — `DAT_00031b64`.
- Инициализация (FUN около строки 13100): из масок `DAT_0003c530` (слоты команды A), `DAT_0003c532` (слоты команды B), `DAT_0003c534` (**слоты под управлением ИИ**). У слотов из c530/c532 владелец = первый бит соответствующей маски (т.е. союзные слоты делят один owner — команда), у слотов из c534 состояние ИИ `DAT_00032aec[slot] = 1`. Сетевой флаг `DAT_000333c0` (1 = сетевая игра; DAT_00031b64 тогда берётся из другой маски).
- Стартовая еда: `FUN_00028b44()` → `DAT_00031c28[owner]` для обоих владельцев (человек и ИИ одинаково). **Еда хранится по владельцу**: `DAT_00031c28[owner]` (u32). Число складов еды: `DAT_00031c48[owner]`. Читы: +5000 / +20000 / +50000 (строки 3280, 3305, 16735).
- `DAT_00032aec[slot]` — **состояние ИИ** слота: 0 = не ИИ (человек/сеть/пусто), 1 = накопление армии, 4 = атака запущена, 5 = (пропускается в «отвязке застрявших»), 7 = только сброс застрявших. Установки: 1 (0x157f1), 4 (0x157fb), 0 (0x157e9).
- Уровень сложности: `DAT_00031aba` ∈ {0,1,2} (задаётся в меню, строка 3035). Влияет на порог атаки (см. §3) и на оценку контратаки: `DAT_000369e4[d] = {0, 400, 1000}` добавка к «силе врага», `DAT_000369f0[d] = {0, 3, 6}` добавка к числу врагов (строки 9321, 9739, 9948). `DAT_000303b2[d] = {15, 0, 15}` — используется при стартовой расстановке (3235/3285).

### Пер-слотовые массивы ИИ (u16 если не сказано иное)
| адрес | смысл |
|---|---|

| 0x32ae4[8] u8 | владелец слота |
| 0x32af4 / 0x32afc / 0x32b04 u8 | выбор врага: `0x32b04[slot]` = **владелец-цель** (берётся из таблицы врагов `DAT_00032d2c[rnd*8 + slot*32 + idx]`, 0x15dd2 / 0x23296 / 0x17e13) |
| 0x32b0c | число юнитов в «группе обороны» (f08=1) |
| 0x32b2c | базовое число обороны (инкремент 0x19722 при создании) |
| 0x32b1c | число созданных «ударных» юнитов (f08=2) |
| 0x32bbc, 0x32b6c | счётчики прибывших/готовых (инкременты 0x18b81/0x18b91) |
| 0x32b7c | таймер цикла атаки (обнуляется при старте атаки) |
| 0x32b3c/0x32b4c/0x32b5c | суммы HP+MP / ATK+DEF / статов из блока игрока для группы обороны (f08=1) |
| 0x32b8c/0x32b9c/0x32bac | те же суммы для остальных юнитов (f08≠1) |
| 0x32c7c | **порог силы для атаки** |
| 0x32bcc[slot*10] | «задача обороны» (10 байт) |
| 0x32c1c[slot*10] | «задача атаки» (10 байт) |
| 0x32f4c[slot*8] u16×4 | прямоугольник (x1,y1,x2,y2) поиска врагов у базы; в образе нули, заполняется в рантайме (запись в декомпиляте не найдена — вероятно при расстановке) |
| DAT_00036684[slot] | = slot*10 (смещение задач) |

Суммы считает `FUN_00015f86` каждый тик (только для живых юнитов типов < 26 со слотом < 8). Блок статистики игрока: `PTR_DAT_00030dd8[slot]` → `0x31c68 + slot*0x138`, внутри по типу смещение `T_TYPE_STATOFF` (12 байт на подвижный тип, 36 на здание).

Формат задачи (10 байт): `[0]` состояние (0 = нет, 4 = есть цель, 8 = искать, 0xC = ждать), `[1]` счётчик ожидания (3), `[2..5]` указатель на юнит-цель, `[6..7]` x (кратно 32), `[8..9]` y.

Группа юнита `U_f08` (+08): 0 = свободен, 1 = оборона базы, 2 = ударная группа.

## 2. Главный цикл и частота

`FUN_00017e1c` (вызывается из основного цикла):
- `g_timerTicks` = BIOS-таймер 0040:006C (18.2 Гц). Игровой тик каждые `DAT_00030098` BIOS-тиков — это и есть скорость из меню (fastest…very slow). Счётчики: `DAT_00031ab4` игровой тик, `DAT_00031b66` = тик & 15.
- В игровом тике: `FUN_00013f4c` (очередь приказов + случайные предметы), `FUN_00015f86` (суммы), затем по каждому юниту: живой → обработчик типа из `DAT_00017fb8[type]` (0x18154 люди/динозавры 1–13, 0x184c8 звери 14–23, 0x18568 строители 24–25, 0x186b3 здания 26–39); мёртвый (флаг +5b бит0) → `FUN_00018058` (таймер восстановления). Потом `FUN_000200fe`, `FUN_0001ab4c` (в т.ч. бегство 0x1ead3), `FUN_0001c340`, `FUN_00015634` (планировщик ИИ). Дальше отрисовка (0x24xxx–0x26xxx).
- «Оглушение» юнита: +43 (0xe4443): младшие 2 бита — короткая пауза, старшие — длинная, уменьшается раз в 4 тика.

### Очередь приказов (общая для человека и ИИ) — `FUN_00013f4c`
Список 10-байтовых записей от `DAT_00033c88` до `PTR_DAT_00033c7c`: `[0]` источник (-1 = локальный), `[1]` код приказа, `[2..3]` индекс юнита, `[4..5]` цель, `[6..7]` x, `[8..9]` y. Каждый тик записи переносятся в юнит: +46 (0xe4446) код, +47 цель (u32), +4b/+4d x,y. В сетевой игре порядок применения меняется (`DAT_000333c0`). Также раз в 32 тика при `DAT_0003c53f` с шансом 51/10000 в случайной точке карты появляется артефакт (`FUN_0001cdf3`, сообщение «Appear the Celestial Sword» и т.д.).

Коды приказов (+46): `0x0f` идти в точку (`FUN_00019f43`), `0x1f` идти к точке (`FUN_00019fbf`, ИИ), `0x37` «сброс/возврат к делу» (`FUN_0001a354`), `0x3f` стоп/инициализация (`FUN_0001a34c`), `0x44` подобрать/охотиться в клетке, `0x6f` умереть, `0xe0/0xe1` меню-команды (`0x19bbe` → таблицы `PTR_LAB_00019ee4/19f08/19f20`), `0xff` нет приказа. При тайловом выравнивании (x&31==0, y&31==0) приказ становится состоянием: +2b (0xe442b) = код, +33 цель, +37/+39 точка.

Состояния юнита (+2b, диспетчер по старшему нибблу): 0x0x покой, 0x1x движение, 0x2x бой, 0x3x «занят/ИИ-ожидание» (0x36–0x3f), 0x4x сбор/охота (0x44, 0x49 приручение), 0x6x смерть (0x6f → 0x60 анимация), 0x7f/0x7e у зданий — заказ/отмена, 0x8x–0x9x действия и магия (`FUN_0001b917`: 0x80–0x91 с расходом «времени» +27).

## 3. Логика ИИ игрока — `FUN_00015634` (0x15634)

Планировщик работает **раз в 32 тика для одного слота** (`slot = (tick>>5)&7`, т.е. каждый слот раз в 256 тиков) через таблицу `PTR_LAB_000156b4[state]`, и **раз в 16 тиков** (`slot = (tick>>4)&7`) через вторую таблицу `0x156d0[state]` для микрозадач. Раз в 128 тиков — `FUN_0001c370` (таймеры предметов на карте: истёкшие убираются, бит 1 клетки снимается). Раз в 8192 тиков — `FUN_00015a0a` → `FUN_00015a3e`: всем юнитам ИИ в состояниях 0x36–0x3f с f08=0 (кроме типа 4 и типов ≥ 0x18) даётся приказ 0x37 — «отвязка застрявших».

### Макросостояния (таблица 0x156b4)
- **state 1 — накопление** (0x156ed): если `sumHP(f08≠1) + sumATKDEF(f08≠1) ≥ порог 0x32c7c[slot]` → перейти в 4 (0x157fb: state=4, таймер 0x32b7c=0), 0x32bbc=0, выбрать цель `0x15b20`: random(50) ≤ 24 → искать **здание** врага-владельца `0x32b04[slot]`; иначе (или если зданий нет) — любой юнит врага; записать в задачу атаки `[0]=4, [2]=цель, [6]=x&~31, [8]=y`. Если врага нет вообще → `[0]=0xC, [1]=3`.
- **state 4 — атака** (0x1572f): когда `0x32b7c ≥ 0x32b1c` (таймер дожил до числа ударных юнитов): random(100) < 50 → `FUN_00015e82` — **создать нового юнита** (копия юнита с f08=2 через `FUN_0001caf0`, помечается f08=2, флаги 3; 0x32b1c++), иначе поднять порог `0x32c7c += 100` (не выше 0x32bac — суммарной силы). Затем state=1, 0x32bbc=0 и всем юнитам с f08=2 приказ идти к точке задачи (`FUN_00015ac6(2)` → `FUN_00019f43`).
- **state 5** (0x157ab): → 1. Состояния 2,3,6,7: ничего.

Порог атаки при старте (FUN_00015da1 / инициализация): `0x32c7c = 200`, +80 если сложность ≠ 2, ещё +80 если ≠ 1 → **easy(0)=360, normal(1)=280, hard(2)=200** (на hard ИИ атакует раньше). Каждому слоту в стартовой инициализации задачи обороны и атаки ставятся в состояние 8 (поиск).

### Микрозадачи (таблица 0x156d0, раз в 16 тиков)
- state 1 → 0x157b7: `0x15885` (задача обороны) + `0x1580e` (задача атаки).
- state 4 → 0x157c6: `0x15885` + `0x158fb`. state 5 → 0x157d6: `0x15982` + `0x158fb`. state 7 → 0x157e1: только отвязка застрявших.
- Автомат задачи (`0x1580e`, `0x15885`, `0x158fb`, `0x15982`): состояние 0 → если счётчик готовых ≥ созданных → 8; **8** → `FUN_00015c07`: найти живого врага (не свой владелец, не в состоянии смерти 0x60–0x6f) внутри прямоугольника `0x32f4c[slot]`, у которого HP < суммарного HP группы и ATK+DEF < суммарного ATK+DEF группы (т.е. ИИ нападает только на заведомо более слабую цель) → `[0]=4, цель`; иначе `[0]=0xC, [1]=3`; варианты 0x158fb/0x15982 ищут ближайшего (чебышёвская метрика) юнита владельца-цели к юниту группы (`FUN_00015ca1`, группа f08=2 или 1), иначе любого юнита этого владельца (`FUN_00015d79`); **0xC** → счётчик--, при 0 → 8.
- Как юниты используют задачи (`FUN_000163e4`, ветка состояний 0x36+): юнит ИИ с f08=1 берёт задачу обороны, с f08=2 — атаки; если у задачи есть цель и она жива — `FUN_00019fbf` (идти/атаковать цель), если цель мертва — задача в 0xC/2; если юнит дальше 160 px (0xa1) от точки задачи — приказ 0x0f идти к точке.

### Производство ИИ — `FUN_00018058` (0x18058, таблица 0x180b4)
Для владельца 8 и для слотов ИИ каждый юнит (живой или мёртвый) ведёт счётчик +4f; порог `T_TYPE_TIMER[type]` (@0x36d82+type*2, для зверей 14–23 плюс `DAT_00033358[type]`, сейчас нули):

| тип | тиков | тип | тиков |
|---|---|---|---|
| 1 human1 | 360 | 9–13 динозавры | 1080 |
| 2,3 | 540 | 14 raptor | 6480 |
| 4 | 720 | 15–18 | 5400 |
| 5–8 (маги) | 540 | 19 mammoth | 8100 |
| 24 / 25 строители | 4500 / 7200 | 20 rhino / 21 tiger | 2880 / 1800 |
| здания 26+ | 540… | 22 brown / 23 wolf | 1080 / 720 |

По истечении:
- **типы 1–13** (0x1ced8): найти своё здание типа `DAT_0001cfa3[type]` (1–3 → 27, 4 → 26, 5→31, 6→32, 7→33, 8→34, 9→35, 10→36, 11→37, 12→38, 13→39; здания строит 26 — святилище), незанятое (`FLAGS50 & 7 == 0`); если стоимость `0x30eac[(b-26)*32+type] (u32, еда за шаг) × 0x315ac[(b-26)*32+type] (u8, число шагов)` ≤ еды владельца → зданию приказ: состояние 0x7f, +33 = тип, +23 = заказчик; таймер = −1 (юнит больше не заказывает). Иначе, если оборона меньше базовой или разница < 5 — `FUN_00015f1c`: перевести до 5 свободных юнитов (состояния 0x2x/0x6x? — `state & 0x60 != 0`, типы < 14) в группу обороны (f08=1). Таймер = 0. Итог: **ИИ воспроизводит армию «по образцу»: каждый живой/погибший юнит периодически заказывает копию самого себя**.
- **типы 14–23** (0x1cfcb): **респаун дикого зверя** на клетке спавна (+59/+5a), полные HP/MP по таблице, состояние 0x3f, снимается флаг смерти, заново ставится на сетку. Т.е. волк возрождается каждые 720 тиков, раптор — 6480.
- **типы 24–25** (0x1d12e): строитель телепортируется на позицию, состояние 0x10, кадр 0x8ed/0x8f5, HP = max.

### Производство в здании (обработчик 0x186b3)
- 0x7f (старт): +09 = число шагов (`0x315ac`), +1f = еда за шаг (`0x30eac`), +1b = уплачено = 0, FLAGS50=1. Каждый тик при FLAGS50&1: если `еда[owner] ≥ шаг` → списать, +1b += шаг, +0a++; когда +0a > шагов → спавн по таблице `0x187d4[b-26]` и FLAGS50=0. Если еды не хватает → FLAGS50|=4 (пауза, для человека — сообщение 0x26d8c). 0x7e — отмена с возвратом уплаченного. Т.е. **оплата идёт постепенно во время обучения**.
- FLAGS50&2 — лечение/починка юнита в здании: HP++ в тик до max. Само здание регенерирует +1 HP раз в 16 тиков (0x18847).
- Смерть здания (0x1886e): для склада еды (тип 0x1e = 30) теряется `еда/(складов+1)` — она рассыпается предметами-едой (`0x1ce37` + `0x1cdf3`, порциями с делением пополам, минимум 50). Если убивший — не человек и здание ИИ — заказчику (+23) ставится счётчик 100 (ускоренный перезаказ).
- Контратака при атаке на здание (`FUN_0001e758`, ветка «My structure is attacked» для ИИ): считается сила врагов в квадрате ±64/+96 px вокруг атакующего (HP+ATK+DEF+MPmax), плюс добавка по сложности; строится список своих юнитов (типы < 26, кроме 4), отсортированный по чебышёвскому расстоянию до здания (до 50 записей, `DAT_000366c4..`), и посылаются ближайшие. (Подробности после `LAB_000162fa` не дочитаны.)

## 4. Поведение отдельного юнита

### Люди/динозавры (0x18154)
1. Раз в 16 тиков `FUN_00018ab2(1)`: +1 HP (люди < 14 только когда HP%4==0 и `FUN_0001c6e9` не съел еду — **лечение за еду из инвентаря**: если в слотах +21..+23 есть предмет 0x1e (еда), `U_COST` (+13, здесь = запас еды у юнита!) уменьшается, при 0 слот очищается), регенерация MP.
2. Если есть приказ и юнит на границе тайла — применить (см. выше); 0x6f — смерть.
3. `FUN_000163e4` (каждые 4 тика, типы ≥ 5): маги 5–8 регенерируют MP, если держат «свой» артефакт (5: предмет 0x11, 6: 0x1d, 7: 0x13, 8: 0x14 в слотах +24..+26). Далее по состоянию:
   - 0x2x (бой): если HP и MP полные и цели нет → 0x3f.
   - 0x3x (≥0x36): ИИ-юниты — следовать задаче группы (см. §3). Не-ИИ/свободные: если счётчик простоя `FLAGS50 > 13` → `FUN_000170f6` сканирует окрестность (кольца `DAT_0003058c[(SPEED>>4)+1]` клеток) на **предметы/еду**, которых юниту не хватает (`FUN_000171d3`: маска нужд по пустым слотам инвентаря +1b..+26: 0x100 слоты 1b–1d, 0x200 1e–20, 0x400 21–23, 0x800 24–26, 0x1000 — нет еды при `U_COST != -1`; класс предмета — биты `T_CLS_FLAGS`) → приказ 0x44 в клетку предмета. **Автосбор для простаивающих.**
   - 0x1x (движение), если +2c==0: оценка угроз `FUN_0001674b` (4 кандидата-реакции, выбор максимума → таблица 0x1680c); для магов 5–8 `FUN_00017014` (поиск по кольцам врага с «умением» +06 == класс-1) и `FUN_00016916`; затем выбор действия/заклинания с максимальной оценкой: `FUN_00016c1f` (лечение: сумма HP своих vs чужих в радиусе, только если своё HP<15), `FUN_00016cb9`, `FUN_00016da7` (атакующее заклинание: сумма HP врагов в радиусе больше своих), `FUN_00016e32`, `FUN_00016eef`, `FUN_00016f16`×3 → таблица `0x16ba0` (индексы 0x24,0x20,0x1c,0x18,0x10,0xc,8,4; первые два только для ИИ). Разрешение каждого действия проверяется битом умений `U_f17` (+17, 4 байта, старт 0x3f) через `FUN_00014873(bit)`.
4. Диспетчер состояния: таблицы `0x182a8` (state<0x80, по старшему нибблу) и `0x182c8` (0x80+: действия).

### Звери (0x184c8)
Лечение, затем на границе тайла `FUN_000172c5`: если простаивает (`FLAGS50 > 13`) и не в 0x4x: сканирование окрестности на еду/цели (`FUN_000170f6`) → приказ 0x44; иначе **случайная точка внутри прямоугольника выпаса** `+55..+58` (±3 тайла от спавна, задаётся в `FUN_0001caf0`) → если проходима (`FUN_0001e609`) → идти (`FUN_00019fbf`). Затем диспетчер `0x1854c` (состояния < 0x70). Дикие звери **не агрессивны сами по себе** — атака возникает через сканирование/повреждение (обработчики урона в другом файле).

### Строители (0x18568)
Анимация 0x10 (счётчик до 0x17) ↔ 0x20; кадры из `0x36f94`/`0x36fac`; каждый тик проверка врагов вокруг `FUN_0001a531` радиусом 4 (тип 24) или 3 (тип 25) → если есть враг → `0x1ead3` (бегство/прекращение работы). Смерть — 0x14 кадров 0x975/0x97a.

### Обнаружение противника
- `FUN_0001a531`/`FUN_0001a526` — обход клеток спиральной таблицы `DAT_000305d0` (пары dx,dy кольцами, `DAT_0003058c` = сколько клеток на радиус: 9,21,29,37,49,61,73,89,101,113,129,145,161,177,189,205,225) начиная с центра `+44/+45`; занятость клетки: `BI>>2 = owner+1` наземного, `MO>>4 = owner+1` летающего; чужой владелец → `FUN_0001a692` (поиск юнита по клетке в списке) и фильтры: свои → только если сам в 0x10/0x30 и цель не умирает; чужие: слот ≥ 8 или ИИ-владелец или тип ≥ 26 → игнорировать (т.е. **ИИ-юниты не реагируют на других ИИ-юнитов и на здания в этом сканере**).
- Радиус видимости (туман для человека) `FUN_0001a3ba`/`FUN_0001a4cc`: бит 0 клетки BI = «открыто», радиус = индекс `SPEED>>4` (скорость 20 → 21 клетка, 90 → 61, 120 → 89, 200 → 161). Радиус сканирования врагов `(SPEED>>5)+1`.

## 5. Движение и поиск пути

### Сетка
- `G_BI_GRID` (0x10ce74, 256 байт на строку, 176 строк): бит0 — открыто (туман), бит1 — на клетке лежит предмет (список предметов `DAT_00031b7c`, записи `0xf4f34+`: тип, x, y, таймеры), биты 2–7 — owner+1 наземного юнита. `G_MO_GRID` (0x117e74): младший ниббл — **направление** стоящего наземного юнита (1..8), старший — owner+1 летающего (тип 0x0b птеро). Постановка/снятие: `FUN_0001e56d` / `FUN_0001e5cc`, `FUN_0001a3db` / `FUN_0001a42c`.
- Проходимость клетки `FUN_0001e685`/`FUN_0001e609` (возврат 1 = свободно, 2 = занято юнитом, 0 = нельзя): вне карты — нельзя; летающий — всегда можно (2 если под ним кто-то); наземный: тайл `u16 BG[y*256+x]` (0xf6e74): если биты 11–15 ≠ 0 → **непроходимо** (объектные тайлы), иначе `DAT_0003183c[tile] & 1` (таблица проходимости 591 байт — в EXE все 1, при загрузке карты заполняется из `TILEn.INF`: значения 0/1/5, бит0 = проходимо). Если клетка занята юнитом — разрешено «проходить сквозь», когда занявший смотрит в ожидаемую сторону (таблицы `DAT_00037910`/`DAT_00037958`: пары допустимых направлений по направлению шага), тогда 2.
- Направления: 1..8 по часовой от севера, `DAT_00030504` = (dx,dy) на тайл, `DAT_0001b852` = пиксельные смещения снаряда/удара, `DAT_000304f6` = октант→направление, `DAT_000377f4` (поворот против) / `DAT_00037818` (поворот по часовой).

### Алгоритм пути — **не A\***
`FUN_0001e11e` (вызывается при движении из 0x1e0e0-области): запускает две симуляции `FUN_0001e399` и `FUN_0001e1c5` — **обход препятствий с «прижатием к стене»** (bug-алгоритм) в зеркальных вариантах поворота:
1. Старт с тайла юнита, цель `+37/+39 >>5`. Направление = к цели (`FUN_0001a95d`), с учётом накопленного отклонения `+3b`.
2. На каждом шаге: пробуем направление; если непроходимо — поворачиваем (одна функция крутит `0x37818`, другая `0x377f4`), максимум 8 поворотов; шаг в первую проходимую клетку; отслеживаем ближайшую к цели точку (`DAT_00037980`/`0x37974` — манхэттен) и на каком шаге она достигнута; лимит **200 шагов** (тогда флаг «не дошёл»).
3. `FUN_0001e11e` сравнивает: меньше шагов → тот вариант; при равенстве — раньше достигнутая ближайшая точка / меньшая дистанция / предпочтение стороны `+3f`. Возвращает 0/1 — какой стороной обходить; фактическое движение — по шагу за тик с проверкой той же проходимости (в `FUN_0001b730/1b7b6` считаются векторы к цели для атаки/выстрела с учётом центра спрайта `T_SPR_CX/CY`).
Итог: юнит не строит полный маршрут, а каждый раз выбирает сторону обхода; в лабиринтах может застревать — отсюда «отвязка застрявших» раз в 8192 тика и лимит 200.

## 6. Что осталось непонятным
- Кто заполняет прямоугольники баз `0x32f4c` и таблицу врагов `0x32d2c` (в образе нули; запись найдена только чтением — вероятно, в коде расстановки сценария, не декомпилированном Ghidra).
- Точная семантика состояний ИИ 5 и 7 (кто их ставит).
- Ветка контратаки после `LAB_000162fa` и обработчик бегства `0x1ead3` (Ghidra не создала функцию).
- Смысл `0x30eac` × `0x315ac`: трактовка «еда за шаг × шаги» даёт цену человека ~1200 еды при `T_STATS_COST=30` — возможно, `U_COST` у юнита это не цена, а переносимый запас еды (см. лечение), тогда таблица 0x37654[6..7] = стартовый запас еды.
- Механика еды у человека (сбор/склад) и боевые формулы — вне темы (другие заметки).
