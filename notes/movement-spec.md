# Движение юнитов — полная спецификация с числами

Цель документа: реализовать движение JW на любом языке, не заглядывая в дизассемблер.
Всё ниже сверено с образом `pwar.img` (база 0x10000) и с портом `reimpl/js/port/move.js`,
который сходится с эталоном (unicorn) байт в байт на 10 000+ шагов.
Смещения полей юнита — от базы записи (см. GAME-LOGIC §4.1).

---

## 1. Система координат и время

- Тайл 32×32 px. Карта до 256×176 тайлов; фактические размеры — `mapW`/`mapH` (GI +0x4a/+0x4e).
- Координаты юнита `X` (+0x2f, i16) и `Y` (+0x31, i16) — **в пикселях**, точка привязки = левый верхний угол тайла.
- Тайл юнита = `X>>5`, `Y>>5`. «Юнит стоит ровно на тайле» ⟺ `X & 0x1f == 0 && Y & 0x1f == 0`
  (в оригинале одна проверка `dword[+0x2f] & 0x1f001f == 0`).
- Цель движения `DSTX` (+0x37, u16), `DSTY` (+0x39, u16) — тоже пиксели, **всегда кратны 32**
  (приказы кладут координату уже как `& 0xffe0`).
- «Прибыл» ⟺ `X == DSTX && Y == DSTY` (в оригинале `dword[+0x2f] == dword[+0x37]`).
- Время: игровой шаг = тик BIOS / делитель скорости (`0x30098`, 1..5). При делителе 1 — 18.2 шага/с.
  Все числа ниже даны в шагах; для секунд делить на 18.2.
- Один вызов шага движения (`0x1dc43`) = один игровой шаг = 4–5 px по каждой активной оси.

## 2. Направления

Направление `DIR` (+0x3d, u16) = 1..8 **по часовой стрелке от севера**; 0 = «нет направления».
Ось Y растёт вниз.

| dir | сторона | Δтайл (dx,dy) | Δpx базовый (`0x37864`) | Δpx доп. (`0x37888`) |
|---|---|---|---|---|
| 1 | N  | ( 0,−1) | ( 0,−4) | ( 0,−1) |
| 2 | NE | (+1,−1) | (+4,−4) | (+1,−1) |
| 3 | E  | (+1, 0) | (+4, 0) | (+1, 0) |
| 4 | SE | (+1,+1) | (+4,+4) | (+1,+1) |
| 5 | S  | ( 0,+1) | ( 0,+4) | ( 0,+1) |
| 6 | SW | (−1,+1) | (−4,+4) | (−1,+1) |
| 7 | W  | (−1, 0) | (−4, 0) | (−1, 0) |
| 8 | NW | (−1,−1) | (−4,−4) | (−1,−1) |

Таблицы в образе: `0x30504[dir]` = (dx,dy) в тайлах (по 2×i16, шаг 4);
`0x30528[dir]` = то же ×32 в пикселях; `0x37864[dir]` = (dy,dx) базовый шаг (внимание: **сначала dy**);
`0x37888[dir]` = (dy,dx) дополнительный шаг.

**Повороты.** `CW[dir] = 0x37818[dir] = [_,2,3,4,5,6,7,8,1]` (по часовой),
`CCW[dir] = 0x377f4[dir] = [_,8,1,2,3,4,5,6,7]` (против).

**Направление на точку** (`0x1a95d`) — чисто по знакам, без учёта модулей:

```
i = 0
if (X != tx) i = (X >= tx ? 6 : 0) + 2
if (Y != ty) i += (Y <= ty ? 3 : 0) + 1
dir = OCT[i],  OCT = 0x304f6 = [0,1,3,2,5,0,4,0,7,8,0,0,6,0,0,0]
```
→ равные координаты дают 0; иначе один из 8 октантов. Следствие: юнит идёт **по диагонали**,
пока обе разности ненулевые, и только потом по прямой (никакой «настоящей» линии Брезенхэма нет).

**Уточнение диагонали** (`0x1a984`, применяется ТОЛЬКО когда +0x3b == 1) — схлопывает диагональ
в ближайшую ось, если |dx| ≠ |dy|:
```
dir 2/6: |dx| < |dy| → dir−1 ;  |dx| > |dy| → dir+1 ;  равны → без изменений
dir 4/8: |dy| > |dx| → dir+1 (9→1) ;  |dx| > |dy| → dir−1 ;  равны → без изменений
```
(в бою для той же задачи используется другая функция `0x1aa10` с порогом «вдвое»: сравнивает
`|dy|>>1` с `|dx|` — см. combat.)

## 3. Сетки, занятость, проходимость

Три параллельные сетки 256×176, индекс клетки `cell = (ty<<8) + tx`:

- **BG** (`u16[cell]`): биты 0..10 — номер тайла, биты 11..15 — **индекс крупной декорации 1..7**
  (0 = ничего): 1–3 кусты, 4–6 пальмы, 7 каменный дольмен; при отрисовке поверх тайла рисуется
  спрайт пака 04 №`2807 + индекс` (рендер — `out/img/bg_overlay_1_7.png`). Это и есть «деревья и
  камни» на карте — отдельного слоя объектов нет, они живут в старших битах BG.
  Если `BG & 0xf800 != 0` — **клетка непроходима** (и не кликабельна).
- **`0x3183c[tileIdx]`** — байт свойств тайла, **напрямую копия файла `TILEn.INF`** (591 байт).
  Проверено по загрузчику: при смене тайлсета из пака 09 запись `ts*2` (TILEn.TRT, 605 184 байта =
  591 тайл × 1024) уходит в 0x49b2c, а запись `ts*2+1` (TILEn.INF, 591 байт) — прямо в 0x3183c.
  Значения в файлах только три: **0 — препятствие, 1 — проходимо, 5 — проходимо + бит 2**.
  Движок читает только бит 0 (в `0x1e685`, `0x1e609`); курсор в UI проверяет `& 3`, но бит 1
  ни в одном тайлсете не встречается, так что это то же самое. **Бит 2 (значение 5) движок
  не читает нигде** — он стоит на тайлах 0–19 (анимированная вода/берег) и ещё на полутора
  десятках, похоже на пометку редактора/аниматора. Контроль: в TILE0 трава (тайл 132) = 1,
  озеро (тайл 567) = 0.
- Не путать с **`0x3e8aa[tileIdx]`** — это цвет тайла на мини-карте, и он **не из INF**:
  `0x24503` при загрузке тайлсета берёт для каждого из 591 тайла один пиксель его битмапа
  по смещению 0x200 (строка 16, столбец 0). Прежняя развилка в GAME-LOGIC §8.2 («INF — это
  проходимость или класс мини-карты») закрыта: проходимость — INF, цвет мини-карты — пиксель тайла.
- **BI** (`u8[cell]`): бит 0 разведано (туман), бит 1 лежит предмет, биты 2..7 = `владелец+1`
  наземного юнита/здания (9 = природа). Проверка «занято» — `BI & 0xfc != 0`.
- **MO** (`u8[cell]`): старший ниббл = `владелец+1` **летающего** юнита (тип 11),
  младший ниббл = **направление наземного юнита, который сейчас в пути в эту клетку** (1..8),
  либо 0, если юнит уже приехал и стоит.

Ключевой инвариант: юнит «занимает» ту клетку, **в которую он идёт**, а не ту, из которой вышел.

> **Клетка юнита — это `+0x53/+0x54`, а НЕ `X>>5, Y>>5`.** Во время диагонального хода пиксельная
> позиция транзитом проходит через «угловую» клетку, которую юнит логически не занимает и которая
> вполне может быть непроходимой (дерево). Пример из трассы: юнит идёт с (29,13) на (30,12), в
> середине хода `X&0x1f = 4`, `Y&0x1f = 28`, и `X>>5, Y>>5` даёт (29,12) — клетку с пальмой.
> Любой код (рендер, выбор мышью, ИИ), выводящий тайл юнита из пикселей, будет иногда ошибаться
> на клетку.
При выходе с тайла: снять отпечаток со старой клетки (`0x1e5cc`), поставить на новую (`0x1e56d`,
пишет DIR в младший ниббл MO, `владелец+1` в биты 2..7 BI и запоминает клетку в +0x53/+0x54).
По прибытии (`arrive`) младший ниббл MO обнуляется — «припаркован».
Поэтому `MO & 0x0f != 0` ⟺ «занявший клетку юнит ещё в движении».

### 3.1 Проверка клетки (`0x1e685`) — можно ли шагнуть

Вход: пиксельные координаты **целевой** клетки и направление шага `dir`. Возврат: код 0/1/2 + флаг «свободно».

```
tx = X>>5; ty = Y>>5
if (tx >= mapW || ty >= mapH)               → 0, занято      // за картой
if (type == 11)                             // летающий
    if ((MO[cell] & 0xf0) == 0)             → 1, СВОБОДНО    // небо пусто
    if ((MO[cell] & 0x0f) == 0)             → 1, занято
    else                                    → 2, занято
if (BG[cell] & 0xf800)                      → 0, занято      // непроходимый тайл
if ((TILEPROP[BG[cell] & 0x7ff] & 1) == 0)  → 0, занято      // INF: не пройти
if (BI[cell] & 0xfc)                        → occ(cell)      // клетка занята юнитом
// «срезание угла» по диагонали: две клетки, через которые проходит диагональ
if (MO[cell + CORNER_OFF[dir][0]] == CORNER_DIR[dir][0]) → occ(...)
if (MO[cell + CORNER_OFF[dir][1]] == CORNER_DIR[dir][1]) → occ(...)
                                            → 0, СВОБОДНО

occ(c) = (MO[c] & 0x0f) != 0 ? 2 : 1        // 2 = занявший в пути, 1 = стоит намертво
```

Таблицы (`0x37910` — смещения i32 парами, `0x37958` — сравниваемые значения по паре байт):

| dir | off₁ | cmp₁ | off₂ | cmp₂ | смысл |
|---|---|---|---|---|---|
| 1 (N)  | 0 | 9 | 0 | 9 | не применяется (9 не бывает) |
| 2 (NE) | −1 | 8 | **+257** | 4 | −1 = клетка (x, y−1) ✔; **+257 — БАГ, должно быть +256** |
| 3 (E)  | +1 | 9 | 0 | 9 | не применяется |
| 4 (SE) | −256 | 2 | −1 | 6 | обе клетки диагонали ✔ |
| 5 (S)  | 0 | 9 | 0 | 9 | не применяется |
| 6 (SW) | +1 | 4 | −256 | 8 | ✔ |
| 7 (W)  | +257 | 9 | 0 | 9 | не применяется |
| 8 (NW) | +256 | 6 | +1 | 2 | ✔ |

Смысл проверки: при диагональном шаге O→T две «угловые» клетки A и B общие для диагоналей
O→T и A→B. Если в одну из них сейчас въезжает юнит по встречной диагонали, шаг запрещён
(иначе два юнита пройдут сквозь друг друга). Смещения даны **относительно T**.

> **Баг оригинала (воспроизводить!):** для dir = 2 (NE) вторая проверка читает клетку
> `T + (1,+1)` = `(x+2, y)` вместо `T + (0,+1)` = `(x+1, y)`. То есть при движении на северо-восток
> встречный юнит, въезжающий на юго-восток в клетку справа, **не** обнаруживается, зато
> ложно срабатывает на клетку через одну. Три остальные диагонали корректны.

## 4. Шаг движения (`0x1dc43`)

Поля: `+0x3b` (u16) — накопленный поворот «вдоль стены» (сколько октантов мы отклонены от прямого
направления), `+0x3f` (u8) — сторона обхода (0 = против часовой, 1 = по часовой),
`+0x40` (u8) — фаза/разрешение обхода, `+0x41` (u8) — счётчик дополнительного шага.

```
step(u):
  # --- А. режим ожидания/разблокировки ---
  if (u[0x40] > 1):
      if (u[0x3b] > 0):  u[0x40]--; idleFrame(u); return DIR       # просто ждём
      blocked = (u[0x40] >= 0x0c)                                  # 12 шагов ждали — хватит
      if (!blocked):
          if (tileCheck(pos + Δpx[DIR], DIR) != СВОБОДНО):
              u[0x40]++; idleFrame(u); return DIR                  # всё ещё занято — ждём
          blocked = true                                           # освободилось — пересчитать
      if (blocked):
          if (X == DSTX && Y == DSTY): return arrive(u)
          p = choosePath(u)                                        # 0x1df84
          if (p.ok): u[0x3f] = p.side; DSTX = p.x; DSTY = p.y
          u[0x40] = 1

  # --- Б. на границе тайла: решаем, куда дальше ---
  if ((X & 0x1f) == 0 && (Y & 0x1f) == 0):
      n = nextDir(u)                                               # 0x1de57
      if (n.dir == 0): return arrive(u)                            # пришли или тупик
      DIR = n.dir
      if (n.wait != 0): u[0x40] = n.wait (=3); return DIR          # шага в этот раз нет
      u[0x3b] = n.turns
      unstamp(u, tile(+0x53,+0x54)); stamp(u, tile + Δtile[DIR])
      if (owner == локальный игрок): revealFog(u)

  # --- В. собственно перемещение ---
  u[0x41] = (u[0x41] - 1) & 0xff
  if (u[0x41] == 0):
      u[0x41] = ((0xff - SPD) >> 5) + 1
      X += Δpx_доп[DIR].dx ;  Y += Δpx_доп[DIR].dy                 # ±1
  X += Δpx_база[DIR].dx ;  Y += Δpx_база[DIR].dy                   # ±4
  X += ALIGN[X & 0x1f] ;   Y += ALIGN[Y & 0x1f]                    # притяжение к сетке
  return walkFrame(u)                                              # 0x1a6e3

arrive(u):
  MO[tile(+0x53,+0x54)] &= 0xf0        # наземный: «припаркован»
  # летающий: MO[cell] = (MO&0x0f) | ((owner+1)<<4)
  if (owner == локальный игрок): revealFog(u)
  return 0                             # 0 = «прибыл», вызывающий переводит состояние
```

**Таблица притяжения `ALIGN` (`0x378d0`, 32 записи i16, индекс `координата & 0x1f`):**
```
idx:  0  1  2  3 ...................... 29 30 31
val:  0 −1 −2  0  0 ... 0 (все нули) ... 0 +2 +1
```
То есть: если координата в пределах 2 px от границы тайла — она **защёлкивается на границу**.
Именно из-за этого дробная прибавка `+1` почти не даёт скорости (см. ниже).

### 4.1 Реальная скорость

Дополнительный шаг `+1 px` делается раз в `N = ((255 − SPD) >> 5) + 1` шагов.
С учётом `ALIGN` установившееся время прохода одного тайла (замерено симуляцией формулы;
от начальной фазы счётчика не зависит):

| N | SPD | шагов на тайл | px/шаг | тайлов/с (18.2) | px/с |
|---|---|---|---|---|---|
| 8 | 0–31 | 8.00 | 4.000 | 2.28 | 72.8 |
| 7 | 32–63 | 8.00 | 4.000 | 2.28 | 72.8 |
| 6 | 64–95 | 8.00 | 4.000 | 2.28 | 72.8 |
| 5 | **96–127** | **7.50** | 4.267 | 2.43 | 77.7 |
| 4 | **128–159** | **8.00** | 4.000 | 2.28 | 72.8 |
| 3 | 160–191 | 7.00 | 4.571 | 2.60 | 83.2 |
| 2 | 192–223 | 7.00 | 4.571 | 2.60 | 83.2 |
| 1 | 224–255 | 6.00 | 5.333 | 3.03 | 97.1 |

Это **потолок** — скорость юнита, у которого счётчик `+0x41` уже «прогрелся» (см. п. 4).

Выводы, важные для реимплементации и баланса:
1. **SPD даёт всего 4 разные скорости** (8, 7.5, 7 и 6 шагов на тайл), разброс от медленного
   к самому быстрому — всего ×1.33.
2. **Диапазон SPD 128–159 — «мёртвая зона»: он медленнее, чем 96–127.** Немонотонность —
   следствие защёлкивания `ALIGN`. Пример из игры: Rhamphorhynchus (SPD 120) быстрее,
   чем Centrosaurus (SPD 150).
3. **Диагональ быстрее прямой в √2 раз**: по каждой оси шаг один и тот же (4 px), значит
   диагональный шаг = 5.66 px пройденного расстояния. Оптимальный маршрут в игре — «сначала
   по диагонали, потом по прямой», что движок и делает автоматически (см. §2).
4. **Счётчик `+0x41` нигде не инициализируется** — ни при создании юнита, ни при старте
   движения; он только уменьшается в самом шаге движения. В файлах карт (OB — снимок памяти
   редактора) у большинства юнитов там **0** либо крупное «мусорное» значение. При `+0x41 = V`
   первая прибавка случится через `V` шагов движения (при `V = 0` — через 256, потому что
   `(0 − 1) & 0xff = 255`). До этого юнит идёт ровно по 4 px/шаг = **8 шагов на тайл при любом SPD**.

   Замер по трассам эталона (учтены только непрерывные проходы тайла, без единого шага ожидания):

   | N | SPD | 6 шагов | 7 шагов | 8 шагов | всего проходов |
   |---|---|---|---|---|---|
   | 1 | 224–255 | 260 | – | 97 | 357 |
   | 2 | 192–223 | – | 5 | 127 | 132 |
   | 3 | 160–191 | – | – | 14 | 14 |
   | 4 | 128–159 | – | – | 365 | 365 |
   | 5 | 96–127 | – | 135 | 1904 | 2039 |
   | 6 | 64–95 | – | – | 1956 | 1956 |
   | 7 | 32–63 | – | – | 799 | 799 |
   | 8 | 0–31 | – | – | 47 | 47 |

   То есть **в реальной игре подавляющее большинство юнитов ходит ровно 8 шагов на тайл**,
   а «паспортная» скорость из таблицы включается только у юнита, который уже сделал `V` шагов
   движения (до 256 шагов ≈ 14 с непрерывной ходьбы). Реимплементация обязана вести `+0x41`
   ровно так же (не инициализировать), иначе юниты поедут быстрее оригинала.

### 4.2 Скорость: где SPD реально важен

Не в перемещении, а в производных величинах:
- **радиус обзора** = `RING_COUNT[SPD>>4]` клеток спирали (§6);
- **радиус поиска цели** (`0x1a526`) = `RING_COUNT[(SPD>>5)+1]` клеток;
- **перезарядка атаки** (состояние 0x12) = `16 − (SPD>>4)` шагов.

## 5. Выбор направления и обход препятствий

### 5.1 Решение на тайле (`0x1de57`)

```
nextDir(u):
  if (X == DSTX && Y == DSTY): return {dir: 0}
  p = choosePath(u)                        # 0x1df84
  if (p.ok): u[0x3f] = p.side; DSTX = p.x; DSTY = p.y
  if (X == DSTX && Y == DSTY): return {dir: 0}     # путь «сдался» — цель = текущая точка

  turns = u[0x3b];  dir = DIR;  saved = turns
  # раскручиваем отклонение обратно к прямому курсу — не более 2 октантов за тайл
  for (k = 0; k < 2 && turns > 0; k++):  turns--;  dir = (u[0x3f] ? CW : CCW)[dir]

  for (try = 0; try < 8; try++):
      if (tileCheck(tile + Δtile[dir], dir) == СВОБОДНО):
          if (turns == 0) u[0x40] = 0                  # вышли на прямую — обход выключен
          return {dir, turns, wait: 0}
      if (u[0x40] < 1): return {dir: DIR, turns: saved, wait: 3}   # обход не разрешён — ждём
      turns++;  dir = (u[0x3f] ? CCW : CW)[dir]                    # крутимся вдоль стены
  return {dir: 0}                                                  # заперты со всех сторон
  # (в оригинале здесь ещё проверка флага 0x377f0, но он всегда 0 — мёртвая ветка)
```

`+0x3b` — это и есть «на сколько октантов мы отвернули от прямого курса, чтобы обойти стену»:
каждый тайл движок пытается вернуть до 2 октантов обратно, а при упоре в стену добавляет.

### 5.2 Нужен ли обход вообще (`0x1df84`)

```
choosePath(u):
  if (u[0x3b] > 1):                        # уже идём вдоль стены — просто проверяем, дойдём ли
      res = ОДНА симуляция по текущей стороне u[0x3f]        # 0x1e19b
      if (res != 0): return {ok:true, side:u[0x3f], x:X, y:Y}  # НЕ дошла → сдаёмся (цель = здесь)
      return {ok:false}                                       # дошла → идём дальше как шли

  dir = dirTo(DSTX, DSTY)                              # 0x1a95d
  if (u[0x3b] >= 1) dir = refine(dir, DSTX, DSTY)      # 0x1a984, см. §2
  DIR = dir;  u[0x3b] = 0
  c = tileCheck(pos + Δpx[dir], dir)
  if (c == СВОБОДНО || c == 2): return {ok:false}      # прямо можно — обход не нужен

  st = STATE(u)
  far = (st == 0x11 || st == 0x31 || st >= 0x50)       # погоня/каст — всегда полный поиск
  if (!far):
      d = max(|DSTX − X|, |DSTY − Y|)                  # чебышёвское расстояние в px
      if (d >= 0xe0):                                  # ≥ 224 px = 7 тайлов
          if (d >= 0x180) return fullPath(u, false)    # ≥ 384 px = 12 тайлов
          far = true
      else:                                            # цель ближе 7 тайлов
          # простая проверка клетки цели (0x1e609: без диагоналей и без «в пути»)
          if (клетка цели СВОБОДНА): far = true         # есть куда идти — ищем путь
          else: return {ok:true, side:u[0x3f], x:X, y:Y}
                # цель непроходима или занята стоящим → DSTX,DSTY := X,Y,
                # т.е. на следующем шаге юнит «прибывает» и переходит в 0x3f
  return fullPath(u, far)

fullPath(u, flag):
  прогнать ОБЕ симуляции (по часовой и против), выбрать лучшую     # 0x1e11e
  res = {ok:true, side, x:лучшая точка X, y:лучшая точка Y, best:лучшая дистанция}
  if (шагов у выбранной стороны < 0xc3 (195)) return res           # путь найден
  if (best <= 0x0f (15 тайлов))              return res            # почти дошли — сойдёт
  res.x = X; res.y = Y; return res                                 # СДАЁМСЯ: цель = где стоим
```

### 5.3 Симуляция «вдоль стены» (`0x1e399` — CCW, `0x1e1c5` — CW)

Это **не A\***: движок дважды «мысленно» проходит от текущего тайла к цели, прижимаясь к стене
левым и правым боком, и берёт лучший из двух результатов. Ничего не запоминается кроме
итога — сам маршрут потом воспроизводится пошагово теми же правилами.

```
wallSim(u, side):                     # side 0: unwind=CCW, scan=CW;  side 1: наоборот
  cur   = (X>>5, Y>>5)                # работаем в тайлах
  goal  = (DSTX>>5, DSTY>>5)
  cnt   = 0                           # сделано шагов
  best  = |goal.x−cur.x| + |goal.y−cur.y|      # манхэттен
  bestCnt = 0;  bestPos = cur
  dir   = DIR;  turns = u[0x3b]
  loop:
      if (cur == goal): result = 0 (успех); break
      if (turns == 0) dir = dirTo(goal)                    # 0x1a95d от текущей клетки
      for (k = 0; k < 2 && turns > 0; k++): turns--; dir = unwind[dir]
      moved = false
      for (try = 0; try < 8; try++):
          c = tileCheck(cur + Δtile[dir], dir)
          if (c == СВОБОДНО || c == 2) { moved = true; break }   # «в пути» считаем проходимым!
          turns++; dir = scan[dir]
      if (!moved): result = 1 (упёрлись); break
      cur += Δtile[dir];  cnt++
      if (cnt >= 0xc8 (200)): result = 1; break            # жёсткий лимит длины
      d = |goal.x−cur.x| + |goal.y−cur.y|
      if (d < best): best = d; bestCnt = cnt; bestPos = cur
  вернуть (result, cnt, best, bestCnt, bestPos*32)
```

Выбор лучшей из двух (`0x1e11e`), по порядку:
1. **меньше `cnt`** (число пройденных тайлов);
2. при равенстве — **меньше `bestCnt`** (раньше добрались до ближайшей точки);
3. при равенстве — **меньше `best`** (ближе подошли);
4. при полном равенстве — сторона из `+0x3f`.

> Симуляция считает клетку, занятую **движущимся** юнитом, проходимой (код 2), а реальный шаг —
> нет (ждёт). Отсюда «толкучка» в узких проходах: путь построен, но юниты стоят в очереди.

### 5.4 Отличия летающих (тип 11, Rhamphorhynchus)

Проверка клетки смотрит только на старший ниббл MO: небо занято другим летающим — нельзя,
иначе можно **всегда**, независимо от рельефа, стен и наземных юнитов. Диагональных проверок нет.
Кадр стойки берётся по формуле ходьбы с `ATKCTR>>1`.

## 7. Кадры анимации ходьбы (`0x1a6e3`)

Счётчик фазы — `+0x2c` (ATKCTR), увеличивается на 1 каждый пройденный шаг, при > 7 сбрасывается в 0.

```
люди/маги (тип < 9):   SPR = BASE_W[тип] + PHASE_H[+0x2c] + DIRO_H[DIR]
звери/динозавры (≥ 9): SPR = BASE_W[тип] + PHASE_B[+0x2c] + DIRO_B[DIR]
стойка (0x1a773):      SPR = BASE_S[тип] + DIRO_S[DIR]      (кроме типа 11)
```

| таблица | адрес | значения |
|---|---|---|
| `PHASE_H` | 0x36e18 | 3, 4, 5, 6, 7, 0, 1, 2 |
| `PHASE_B` | 0x36e28 | 0, 0, 1, 1, 2, 2, 3, 3 (каждый кадр держится 2 шага) |
| `DIRO_H`  | 0x36e68 | dir 1..8 → 0, 8, 16, 24, 32, 24, 16, 8 |
| `DIRO_B`  | 0x36e7a | dir 1..8 → 0, 4, 8, 12, 16, 12, 8, 4 |
| `DIRO_S`  | 0x36e06 | dir 1..8 → 0, 1, 2, 3, 4, 3, 2, 1 |
| `BASE_W`  | 0x36e38 | типы 1..8: 5, 70, 135, 200, 265, 330, 395, 460 (блок 65 кадров); типы 9..23: 1690, 1730, … 2250 (блок 40) |
| `BASE_S`  | 0x36dd6 | типы 1..8: 0, 65, 130, …, 455; типы 9..23: 1685, 1725, … 2245 |

Симметрия `DIRO_*` (dir 6=4, 7=3, 8=2) означает, что спрайты для западных направлений —
**отражённые по горизонтали** копии восточных; кадров для 8 направлений в файлах только 5.

## 8. Точки входа: как юнит вообще начинает идти

1. Приказ (из UI, ИИ или сети) кладётся в `+0x46` (код), `+0x47` (цель), `+0x4b/+0x4d` (X,Y).
2. Отложенный приказ применяется **только когда юнит стоит ровно на тайле**: код становится
   состоянием `+0x2b`, точка — `+0x37/+0x39`.
3. Состояние **0x0f** = «начать движение» (`0x1db94`):
   - если владелец под ИИ и у юнита открыто умение 0x1a (телепорт) и чебышёвское расстояние
     до цели ≥ `0x140` (320 px = 10 тайлов) — вместо ходьбы выдаётся приказ заклинания 0xb2;
   - иначе: `+0x3b = 0`, `+0x40 = 0`, `+0x2c = 0`, `DIR = dirTo(цель)`, кадр стойки,
     отпечаток на текущей клетке; состояние → **0x00**.
4. Состояние **0x00** — каждый шаг вызывается `step()` (§4). Возврат 0 («прибыл») →
   счётчики `+0x52`++ и переход в 0x3f (охрана/простой); у Constructor'а с заказом стройки —
   превращение в здание.
5. Прочие состояния используют то же движение как подпрограмму: 0x10/0x11 (сближение с целью),
   0x37 (возврат на пост), 0x4x (охота/добыча), 0x50 (перенос предмета), 0x8x (подход для каста).

## 9. Сводка «странностей», которые нужно повторить

1. `+257` вместо `+256` в диагональной проверке для направления NE (§3.1).
2. Немонотонная скорость по SPD: 128–159 медленнее, чем 96–127 (§4.1).
3. Счётчик `+0x41` не инициализируется при старте движения (§4.1 п.4).
4. Направление на цель — по знакам разностей, без модулей: диагональ до упора (§2).
5. Симуляция пути оптимистична (движущийся юнит = проходим), реальный шаг — нет (§5.3).
6. При недостижимой цели юнит не «не идёт», а **переставляет себе цель в текущую точку**
   и сразу «прибывает» (§5.2, `fullPath`).
7. Лимит симуляции 200 тайлов, порог «сдаться» 195 шагов и 15 тайлов остатка (§5.2).
8. Ожидание в заторе: не более 12 шагов, потом полный пересчёт пути (§4, ветка А).
9. Мёртвый код, который можно не переносить: флаг `0x377f0` (всегда 0, ветка недостижима),
   флаги `0x377f1` и `0x37988` (пишутся, но нигде не читаются), проверка `d >= 0x180`
   внутри ветки `d < 0xe0` в `choosePath`, а также условие `st >= 0x80 || st >= 0x50`
   (второе поглощает первое).

## 10. Как это проверено

Документ не пересказывает дизассемблер, а сверен с эталоном:

- `tools/spec_check_move.py traces/*` — **независимая** реализация §4 (шаг движения: счётчик
  дополнительного шага, базовый шаг, `ALIGN`) на Python по тексту этого документа; берёт
  состояние юнита на шаге k из трассы unicorn-эталона, применяет формулу и сравнивает с шагом k+1.
  Результат: **63 827 переходов совпало, 0 расхождений**, состояния 0x00, 0x11, 0x31, 0x36, 0x42,
  63 разных значения SPD от 20 до 255 (все восемь диапазонов N). Состояние 0x60 (труп) шаг
  движения не вызывает — исключено.
- `tools/spec_check_speed.py traces/*` — замер непрерывных проходов тайла (таблица в §4.1 п. 4).
- `tools/spec_check_tiles.py traces/*` — проверка предиката проходимости из §3.1 (`BG & 0xf800 == 0`
  и бит 0 в `TILEn.INF`) на всех занятых клетках всех трасс: **1 098 921 наблюдение, 0 нарушений**.
  Единственное исключение — 142 наблюдения одного леопарда на карте 2, которого редактор поставил
  стартовой расстановкой на непроходимую клетку: движок проверяет только клетку, **в которую**
  шагают, и такую расстановку молча терпит. На этой же проверке и обнаружилось, что клетку юнита
  нельзя выводить из пикселей (врезка в §3).
- Пути и таблицы обхода дополнительно покрыты штатной сверкой порта:
  `node js/test/fntest.mjs cases/{mv_*,mvstep_*,next_*,tile*,dir00*}` и
  `node js/test/compare.mjs traces/m0_t0`.

Запуск: из `reimpl/`, например
`python3 ../tools/spec_check_move.py traces/long_m2_t0 traces/long_m9_t3`.
