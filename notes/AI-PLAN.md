# План действий, нюансы и подводные камни

Проект: внедрение обучаемого ИИ в 2D-стратегию (порт с DOS, тема «парк юрского периода»), JavaScript, инференс на CPU в браузере / desktop / Android.

---

## Часть 0. Ключевые вводные проекта

| Параметр | Значение | Следствие для архитектуры |
|---|---|---|
| Состояние игры | ~100 КБ, плоский участок памяти | Легко снапшотить, легко сериализовать в тензоры, дёшево прогонять симуляции |
| Карта | Клеточная, вид сверху, 2D спрайты | Подходит CNN по слоям карты |
| Ресурс | Один (еда) | Простой экономический вектор, мало измерений |
| Юниты одновременно | ~20–30 на команду | Можно позволить отдельный проход сети на каждого юнита |
| Туман войны | Открывается **навсегда**, не затемняется | Не нужна память об устаревании; достаточно бинарной маски «открыто/нет» |
| Реплеи | Отсутствуют полностью | Данные только из симуляции + собственной игры |
| Целевая платформа | CPU (браузер, desktop, Android) | Модели десятки–сотни тысяч параметров, не больше |
| Цель | Много конфигураций ботов | Параметр стиля/сложности на входе или отдельные веса |

## Часть 1. Итоговая архитектура

```
                    ┌─────────────────┐
                    │    СТРАТЕГ      │  вся карта (сжато), фаза игры,
                    │  раз в N сек    │  зоны сил, косвенные признаки врага
                    └────────┬────────┘  → намерение + приоритеты построек
                             │
                    ┌────────▼────────┐
                    │     ТАКТИК      │  локальная зона боя, сводка сил,
                    │  раз в ~секунду │  намерение стратега, короткая память
                    └────────┬────────┘  → роли + веса важности + охват
                             │
              ┌──────────────┼──────────────┐
        ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
        │   ЮНИТ    │  │   ЮНИТ    │  │  СТРОИТЕЛЬ│   ОДНА И ТА ЖЕ СЕТЬ
        │ каждый шаг│  │ каждый шаг│  │ каждый шаг│   (параметрический шеринг)
        └───────────┘  └───────────┘  └───────────┘
```

**Правила потоков данных:**
- Стратег **не общается с юнитом напрямую** — только через тактика.
- Тактик может **сигнализировать наверх** (например, «не хватает такого типа юнита»), но не решает про постройки.
- Постройки и экономика — зона **стратега**.
- Здания — это тоже юниты, просто с другим вектором признаков (не могут двигаться и т.п.).
- Строитель — тоже юнит, но с **отдельной ролью** и собственной наградой за выживание (он дорогой и слабый).

## Часть 2. Спецификация входов и выходов

### 2.1 Юнит (Исполнитель)

**Вход:**

| Блок | Содержимое |
|---|---|
| Собственные характеристики | тип юнита (one-hot или embedding), здоровье (норм. 0–1), несомый ресурс, скорость, дальность атаки, урон, уровень прокачки |
| Локальное окружение | «вырезка» карты вокруг юнита, радиус R клеток, слоями: местность / свои юниты / чужие юниты / ресурсы / здания / маска открытости |
| Приказ сверху | роль (one-hot из фикс. набора) + вес важности (3 дискретных уровня на старте) + цель приказа (координата или id объекта) |
| История | последние 2–3 действия (one-hot), опционально координата предыдущей позиции |

**Выход:** softmax-распределение по доступным командам + (при необходимости) целевая координата/цель. Действие **сэмплируется**, не argmax.

**Набор ролей (стартовый, ограниченный):**
1. `ATTACK_TO_DEATH` — уничтожить цель
2. `DISTRACT` — отвлечь и увести, не обязательно убивать
3. `DEFEND_POINT` — удерживать точку/здание
4. `FARM` — набивать опыт/ресурс
5. `GATHER` — собирать еду
6. `RETREAT` — отступить, сохранить себя
7. `ESCORT_BUILD` — дойти до точки и развернуть здание (для строителя)
8. `IDLE_GUARD` — стоять, реагировать при появлении угрозы

> Начинай с 5–6 ролей. Каждая новая роль — это отдельный набор сценариев и отдельная формула награды. Роли добавляются итеративно.

### 2.2 Тактик

**Вход:** локальная зона боя (радиус больше юнитского, слоями) · сводная статистика стычки (число и суммарное HP своих/чужих, соотношение сил) · вектор намерения стратега · короткая память по стычке.

**Выход:** для каждого юнита/группы в зоне — `(охват, роль, вес важности, цель)`.

**Охват** — параметр команды, а не отдельная архитектура:
- `ALL` — вся группа (низкая категоричность по умолчанию)
- `SUBGROUP` — несколько юнитов
- `SINGLE` — конкретный юнит (высокая категоричность)

### 2.3 Стратег

**Вход:** сжатая карта (downsample, зоны вместо клеток) · экономика (еда, здания по типам, очередь строительства) · фаза игры и время · косвенные признаки о противнике из открытой информации (замеченные здания, наблюдаемый темп, агрессивность).

**Выход:** глобальное намерение (экономика / оборона / атака в зону X) + приоритеты построек.

**Категорически нельзя:** давать стратегу данные из-под тумана войны. Ни при инференсе, ни при обучении.

## Часть 3. План действий по этапам

### Этап 0. Подготовка движка (без всякого ИИ)

1. **Headless-режим симуляции.** Отделить игровую логику от рендера. Игра должна прогоняться без графики и без привязки к реальному времени, максимально быстро.
2. **Детерминированный seed.** Симуляция должна воспроизводиться один в один по seed — иначе отладка обучения превратится в ад.
3. **Сериализация состояния → тензоры.** Функция, превращающая снапшот игры в слои карты + векторы признаков. Это фундамент всего, писать аккуратно.
4. **Формализовать набор команд.** Составить конечный список игровых команд, которые движок принимает — это одновременно и выход юнита, и выход тактика.
5. **Логирование пар (состояние → команда)** для будущей записи датасетов, в том числе при обычной игре человеком.
6. **Параллельный запуск N симуляций** на разных ядрах CPU (worker threads / отдельные процессы).

> **Подводный камень:** пункты 1–3 люди обычно недооценивают. Если симуляция медленная или недетерминированная, всё остальное не взлетит, сколько бы ты ни возился с сетями.

### Этап 1. Скриптовый бот (временный, но необходимый)

1. Написать простой прямолинейный скриптовый бот. Топорность — ожидаема и допустима.
2. Заложить **2–4 разных стиля**: агрессивный, экономический, оборонительный, смешанный.
3. Добавить **рандомизацию решений** и **рандомизацию стартовых условий** (позиции, количество ресурсов, расположение врагов).
4. Прогнать тысячи партий скрипт vs скрипт, записать датасет.

> **Подводный камень:** не пытаться сделать скриптового бота хорошим. Он нужен только чтобы у сети была разумная отправная точка, а не случайное блуждание. Хороший скрипт = потерянные недели.

### Этап 2. Юнит через Behavior Cloning

1. Собрать датасет из этапа 1: `(вход юнита) → (команда скрипта)`.
2. **Фильтровать данные через туман войны** — подавать только то, что бот мог видеть.
3. Обучить сеть обычным supervised-способом (backprop, cross-entropy по распределению команд).
4. Проверить: ведёт ли себя сеть хотя бы как скрипт.

> **Подводный камень (критический):** если обучающие данные содержат решения, принятые со знанием полной карты, бот будет «читерить» неявно — он выучится делать правильные вещи по неполным данным, что выглядит как экстрасенсорика. Данные должны быть честными на этапе записи, а не на этапе инференса.

### Этап 3. Юнит через RL на мини-аренах

1. Построить **маленькие тренировочные арены** — не вся карта, а квадрат вокруг юнита с расставленными врагами/зданиями.
2. Под **каждую роль** — свой набор сценариев и своя формула награды.
3. Процедурно нагенерировать сотни вариаций по шаблону (количество врагов, направления, HP, дистанции). Здесь уместно делегировать генерацию LLM.
4. Обучать **actor-critic**: actor выбирает действие, critic оценивает ситуацию сразу, не дожидаясь конца эпизода.
5. Стартовать не с нуля, а с весов из этапа 2.

**Формулы наград по ролям (стартовые ориентиры):**

| Роль | Терминальная награда | Shaping (малые веса) |
|---|---|---|
| `DISTRACT` | + за долю врагов, переключившихся на юнита; + за оставшееся HP защищаемого объекта; + за время жизни объекта; + за выживание юнита | + за факт агро на себя; − за полученный урон |
| `ATTACK_TO_DEATH` | + за уничтожение цели; − если цель дошла/выжила | + за нанесённый урон; − за полученный |
| `DEFEND_POINT` | + за HP точки в конце; + за время, которое точка продержалась | − за уход далеко от точки |
| `FARM` | + за накопленный опыт/ресурс за эпизод | − за полученный урон; − за простой |
| `GATHER` | + за доставленный ресурс | − за пройденное лишнее расстояние |
| `ESCORT_BUILD` | ++ за развёрнутое здание; −− за смерть строителя | − за полученный урон |
| Общее для всех | − за смерть; − за осцилляцию (движение туда-обратно N шагов подряд) | − небольшой штраф за каждый шаг (побуждает не тянуть) |

> **Подводный камень:** shaping-награды **должны быть существенно меньше** терминальных. Иначе получишь берсерка, который оптимизирует «нанесённый урон» и никогда не отвлекает и не отступает. Это самая частая ошибка, и обнаруживается она только по странному поведению — численно всё будет «сходиться».

### Этап 4. Оценка юнита

1. Держать **отдельный набор тестовых сценариев**, на которых **не обучаешь**.
2. Смотреть глазами: выглядит ли поведение разумным и правдоподобным.
3. Проверять переносимость: сценарии, которых не было в обучении (другое число врагов, другая геометрия).

> **Подводный камень:** высокая награда на тренировочном наборе ≠ хорошее поведение. Сеть охотно зазубривает набор. Разделение train/test обязательно.

### Этап 5. Тактик

1. **Сначала** — imitation learning от человека: интерфейс, где ты видишь ровно то, что видел бы тактик, и выдаёшь приказы обычными игровыми командами.
2. Логировать пары `(состояние → приказ)`, включая «молчание» = «продолжай прежний приказ».
3. Обучить behavior cloning.
4. Затем — RL на сценариях уровня **стычек** с несколькими юнитами, поверх **уже обученного** юнита.
5. Награда тактика — **только за исход стычки**, не за микро-действия юнитов.

> **Подводные камни:**
> - Не давать человеку в интерфейсе больше информации, чем будет у тактика. Иначе датасет нечестный — та же ошибка, что с туманом войны.
> - Не обучать тактика поверх необученного юнита. Два случайных уровня одновременно = шум, обучение почти не идёт.
> - Не строить конвертер «клик → абстрактный вектор». Выход тактика = существующие игровые команды движка.
> - Не обучать на сырых кликах/координатах. Игра уже интерпретирует клик как осмысленное действие («атаковать вот этого») — это и есть чистый сигнал. Сырой клик содержит промахи, передумывания и моторный шум.
> - Дискретизировать вес важности на старте (3 уровня, не непрерывная шкала 0–100). Это прямой аналог «контуров вместо сырого видео» — резко сужает пространство обучения. Тонкую шкалу сеть освоит потом сама через self-play.

### Этап 6. Стратег

1. Imitation learning от человека на упрощённом интерфейсе уровня всей карты, редкие решения.
2. RL на **уменьшенных полных партиях**: маленькая карта, ограниченный набор построек и юнитов, партии от начала до конца.
3. Curriculum: постепенно увеличивать карту и добавлять типы построек/юнитов.
4. Награда — исход всей партии / крупного отрезка (победа, поражение, экономический рост).
5. Обучать **поверх уже обученных** тактика и юнита.

> **Подводный камень:** сорокаминутные полные партии на старте обучения — сигнал слишком редкий и зашумлённый, стратег не поймёт, какое из его решений на пятой минуте повлияло на итог. Начинать с коротких упрощённых партий обязательно.

### Этап 7. Self-play и разнообразие

1. Дообучать всю пирамиду через игру против собственных прошлых версий.
2. Держать **пул старых версий** (не только последнюю), иначе агент переобучится под одного конкретного противника.
3. Для разных конфигураций ботов: либо параметр стиля на входе стратега, либо отдельные веса под каждый стиль.
4. Регулировать сложность бота: температура сэмплирования, урезание набора доступных ролей, ограничение частоты решений стратега.

## Часть 4. Сводный список подводных камней

### Данные и честность
1. **Читерство через данные.** Обучение на решениях, принятых со знанием всей карты, даёт бота, который «знает» больше, чем видит. Фильтруй датасет через туман войны на этапе записи.
2. **Асимметрия информации при imitation learning.** Человек в отладочном интерфейсе не должен видеть больше, чем сеть.
3. **Сырые входы вместо осмысленных.** Пиксели клика, координаты мыши, необработанные траектории — шум. Подавать интерпретированные игровые действия.

### Награды
4. **Слишком большие shaping-награды.** Агент оптимизирует подсказку вместо цели. Самая частая и самая незаметная ошибка.
5. **Бинарная награда там, где нужна градуированная.** «База выжила / не выжила» не даёт понять, что «умерла медленнее» — лучше. Нужны частичные величины: остаточное HP, время жизни, доля отвлечённых, число выживших.
6. **Одна универсальная награда на все роли.** Награда для «отвлечь» и для «уничтожить» — противоположные вещи. Каждая роль — своя формула.
7. **Веса между компонентами награды — вопрос дизайна, не математики.** Их придётся подбирать итеративно, это нормальная часть процесса.

### Архитектура и обучение
8. **Детерминизм модели.** Одинаковый старт → одинаковая партия. Лечится **сэмплированием из распределения**, а не подмешиванием даты/времени (сеть проигнорирует признак, который при обучении ничего не значил).
9. **Осцилляция без истории.** Юнит ходит туда-сюда, потому что каждый кадр состояние «переубеждает» его. Лечится историей последних действий + штрафом за осцилляцию.
10. **Обучение уровней в неправильном порядке.** Только снизу вверх: юнит → тактик → стратег. Верхний уровень нельзя обучать над случайно ведущим себя нижним.
11. **Смешанный сигнал ответственности (credit assignment).** Не обучать тактика и юнита от одной и той же награды. У каждого своя зона: юнит отвечает за исполнение роли, тактик — за выбор ролей.
12. **Переобучение на тренировочных сценариях.** Обязателен отдельный тестовый набор.
13. **Смешение уровней абстракции бесструктурно.** Охват приказа (вся группа / подгруппа / один юнит) должен быть явным параметром команды, а не подразумеваться.

### Инфраструктура
14. **Медленная симуляция.** Главное бутылочное горлышко всего проекта. Оптимизировать headless-логику, параллелить по ядрам.
15. **Попытка перенести симуляцию на GPU.** Это делают только большие исследовательские команды (Google, OpenAI) для миллиардов эпизодов. На твоём масштабе не окупится — потратишь месяцы. GPU нужен максимум для backprop, и то не обязательно.
16. **Недетерминированная симуляция.** Отладка обучения станет невозможной. Seed обязателен.
17. **Раздутие модели.** Целевая платформа — CPU в браузере и на Android. Держать модели в пределах десятков–сотен тысяч параметров.

### Процесс
18. **Попытка продумать все сценарии вручную.** Не нужно и невозможно. Достаточно разнообразного набора — сеть обобщает на похожие ситуации.
19. **Полировка скриптового бота.** Он временный. Не вкладывать в него силы.
20. **Ожидание полной автономности от LLM.** LLM может генерировать вариации сценариев, писать код арен, прикидывать стартовые награды — но не может оценить, «выглядит ли поведение тупо» в твоей игре. Человек остаётся точкой контроля качества.

## Часть 5. Порядок работ — краткий чеклист

- [ ] Headless-симуляция, детерминированный seed, параллельный запуск
- [ ] Сериализация состояния → тензоры (слои карты + векторы)
- [ ] Формализованный список игровых команд
- [ ] Логирование пар (состояние → команда) при игре человеком
- [ ] Скриптовый бот, 2–4 стиля, рандомизация
- [ ] Датасет из тысяч авто-партий, фильтрованный через туман войны
- [ ] Behavior cloning юнита
- [ ] Мини-арены по ролям + процедурная генерация вариаций
- [ ] Формулы наград по ролям, подбор весов shaping

## Часть 6. Терминология (для поиска и чтения материалов)

| Термин | Что означает в контексте проекта |
|---|---|
| **Behavior cloning** | Обучение с учителем на парах «ситуация → команда», взятых у скрипта или человека |
| **Imitation learning** | То же, но источник — человек через интерфейс |
| **Policy gradient** | Метод RL: увеличивать вероятность действий, приведших к хорошему исходу |
| **Actor-critic** | Actor выбирает действие, critic оценивает ситуацию сразу, ускоряет обучение |
| **Reward shaping** | Малые промежуточные награды для ускорения обучения |
| **Credit assignment** | Проблема «кто виноват в исходе» — тактик или юнит |
| **Partial observability** | Неполная наблюдаемость (туман войны) |
| **Parameter sharing** | Одна сеть на все типы юнитов, тип подаётся как признак |
| **Hierarchical RL** | Иерархия «стратег → тактик → юнит» |
| **Curriculum learning** | Постепенное усложнение сценариев |
| **Self-play** | Обучение игрой против собственных прошлых версий |
| **Procedural scenario generation** | Автоматическая генерация вариаций тренировочных сцен |

## Встроенный ИИ оригинала: устройство, отделимость, цена (11.09.2026)

**Устройство — автомат состояний на племя, не думание за каждого юнита.** На слот (их 8) —
байт состояния `0x32aec+s` (0 = выключен, 7 состояний), рядом таблицы: враги слота `0x32d2c`,
текущая цель `0x32b04`, таймеры `0x32b7c`, пороги силы `0x32c7c`, счётчики групп `0x32b0c/0x32b1c`.
Диспетчер `F[0x15634]` зовётся в конце шага и крутит слоты по младшему байту счётчика шагов:
раз в 32 шага — стратегический такт слоту `lo>>>5` (таблица `TAB_156b4`), раз в 16 шагов —
тактический такт слоту `(lo&0x70)>>4` (таблица `TAB_156d0`). Каждое племя думает ≈2 раза в секунду.

**Уровень решений — племя, дальше группы.** ИИ помечает юнитов байтом группы `U.F08`
(0 праздный, 1 оборона, 2 ударная), набирает оборону до 5 (`F[0x15f1c]`), выбирает цель
(`F[0x15b20]`, 50/50 здания или юниты) и выдаёт группе приказ идти в точку `F[0x15ac6]`.
Приказ пишется теми же примитивами, что и клик игрока: `F[0x19f43]` кладёт `U.ORDER=0x0f` и
точку назначения, `F[0x1a354]` — «вернуться на пост». Своего движения/боёвки у ИИ нет.
Разница с игроком одна: он минует слой клика и очереди (`0x1419e`/`0x14895`) и пишет поля напрямую.

**Отделимость — полная, по конструкции оригинала.** Байт включения на слот; при нуле диспетчер
выходит сразу (так кампания и включает компьютер только нужным племенам). Плюс у нас весь
диспетчер — одна функция в `F[]`, подменяется на лету.

**Цена (миссия 11, 462 юнита, 7 ИИ-слотов):** тик без ИИ 0.098 мс, с ИИ 0.109 мс → 0.011 мс,
это 11.5 % тика и 0.2 % бюджета в 55 мс.

**Цена решения нашего ИИ:** кодирование наблюдения 1.7 мкс/юнит; прямой проход сети (ppo11)
**1.83 мс**. 50 юнитов с решением раз в 8 тиков → 11.4 мс/тик; 200 юнитов → 45.8 мс (впритык).

**Куда ставить.** Скриптовый ИИ — в `наШаг` (туда же, где artifacts.js и buildplan.js): нулевая
задержка, детерминизм, но только целочисленная арифметика и общий ГСЧ. Нейросеть — снаружи,
считает хост, приказы уходят обычными пакетами хода (задержка = один ход, как у живого игрока);
внутрь шага её нельзя из-за расхождения плавающей точки между браузерами.

**Форк движка — нет.** Функции подменяются по адресу, для своей логики есть `наШаг` и `НАШИ`;
артефакты доказали, что механику можно держать за флагом и при выключенном флаге память
совпадает побайтово. Две версии движка не живут в одной сетевой партии (разойдётся хеш).
Песочница = набор флагов на одном движке, а не вторая копия.
