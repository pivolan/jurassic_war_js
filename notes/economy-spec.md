# Экономика, здания и добыча — полная спецификация с числами

Цель документа: реализовать экономику JW на любом языке, не заглядывая в дизассемблер.
Всё ниже прочитано из `pwar.img` (база 0x10000, `file_offset = addr − 0x10000`), взято из порта
`reimpl/js/port/economy.js` (сверен с эталоном под unicorn байт в байт) и **эмпирически подтверждено**
на трассах эталона и на сценариях под unicorn — см. §15 «Как это проверено».

Смещения полей юнита — от базы записи (GAME-LOGIC §4.1). Время — в игровых шагах;
при делителе скорости 1 это 18.2 шага/с (см. movement-spec §1).

Машинные копии всех крупных таблиц: `reimpl/data/economy_*.json`
(генератор — `tools/spec_dump_economy.py`).

## 1. Общая картина

Ресурс в игре ровно один — **еда (Foods)**. Она существует в трёх независимых «карманах»:

| карман | где лежит | кто тратит |
|---|---|---|
| **склады игрока** | `u32[8]` по адресу `0x31c28`, индекс = владелец | производство в зданиях, выдача со склада |
| **ноша юнита** | поле `FOOD` (+0x13, u16) каждой записи юнита | лечение юнита, покупка в арсенале |
| **кучки на земле** | пул объектов OI, 500 записей по 16 байт от `0xf4f34` | подбирается юнитами |

Перекачка между карманами:
- земля → ноша: подбор (состояние 0x4x, §11.1);
- ноша → склады: сдача носильщиком (состояние 0x5x на склад, §11.2), **всё сверх 50 за один шаг**;
- склады → земля: выдача из меню склада (§9.2);
- ноша → ноша: передача другому юниту (половина), продажа предмета в арсенале;
- ноша → воздух: лечение (1 еда на каждый 4-й HP), покупка предмета в арсенале (см. баг §14.6);
- склады → воздух: производство, гибель склада (§9.3).

Счётчик складов `g_nStorage[8]` = `u32[8]` по адресу `0x31c48`. Он нужен **только** для дележа еды
при гибели/захвате склада (§9.3) и для показа числа еды в HUD.

Стартовая еда берётся из сценария (по `notes/economy-buildings.md` — GI +0x14; сам я это поле
не проверял). Наблюдаемые в трассах значения: миссия 0 — 0/1000, м. 2 — 2000/15000,
м. 5 — 5000/150000, м. 9 — 200000/10000 — то есть числа зашиты в файлы миссий и сильно разнятся.

## 2. Еда у юнита: поле FOOD и слоты инвентаря

Инвентарь юнита — 12 байт `+0x1b..+0x26`, в каждом байте id предмета (0 = пусто).
Группы слотов жёсткие (см. §10.1, флаги предмета):

| слоты | группа |
|---|---|
| 0..2 (`+0x1b..+0x1d`) | оружие |
| 3..5 (`+0x1e..+0x20`) | щиты |
| 6..8 (`+0x21..+0x23`) | расходники **и еда** (id 0x1e = «Foods») |
| 9..11 (`+0x24..+0x26`) | артефакты |

Количество еды хранится не в слоте, а в отдельном поле `FOOD` (+0x13, u16); слот 0x1e — просто
отметка «еда есть». При создании юнита `+0x21 = 0x1e`, а `FOOD` берётся из таблицы статов (§3).

> **Внимание для реимплементации:** у **зданий** те же байты переиспользованы под заказ производства:
> `+0x1b` (u32) = уплачено, `+0x1f` (u32) = еда за шаг, `+0x23` (u32) = указатель на заказчика.
> Инвентаря у зданий нет.

**Добавить еду (`0x1c679`, вход `ax` = сколько):**
```
слот = первый из 6..8 со значением 0x1e
если такого нет: слот = первый из 6..8 со значением 0; если и такого нет — ОТКАЗ (ax не меняется)
                 иначе пометить его 0x1e
sum = FOOD + ax
если sum > 0xffff:  FOOD = 0xffff;  вернуть ax = sum & 0xffff   # «остаток», который не влез
иначе:              FOOD = sum;     вернуть ax = 0
```

**Списать еду (`0x1c6e9`, вход `ax`):**
```
если FOOD < ax:                       ОТКАЗ (ax не меняется)
если нет слота 6..8 со значением 0x1e: ОТКАЗ
FOOD -= ax;  если FOOD == 0 — очистить слот;  вернуть ax = 0
```
То есть **возврат 0 = успех**, ненулевой возврат = отказ.

## 4. Голод и лечение (`0x18ab2`)

Регенерация вызывается **раз в 16 шагов** — когда счётчик `0x31b66` (инкремент каждый шаг,
маска 0x0f) равен 0. Вызов идёт из обработчиков типов: `0x18154` (люди и ручные динозавры 1..13),
`0x184c8` (дикие звери 14..23), `0x18568` (растения 24/25). Аргумент `al` всегда 1.

```
regen(u, al=1):
  if STATE == 0x6f: return                       # уже умирает
  if HP < HPMAX:
      heal = true
      if TYPE < 14 and (HP & 3) == 0:            # каждый 4-й HP платный
          heal = (списать 1 еду из FOOD получилось)
      if heal:
          HP = min(HP + al, HPMAX)               # с промежуточным насыщением до 255
  if MANA < MAG:
      MANA = min(MANA + al, 255)
      if MANA > MAG: HP = MAG                    # <-- БАГ ОРИГИНАЛА: пишет в HP, а не в MANA
```

Числа:
- **скорость лечения — 1 HP за 16 шагов** (≈0.88 с), независимо от типа и статов;
- **цена лечения — 1 еда на каждые 4 HP** (платят только типы 1..13);
- если еды нет (FOOD = 0 или нет слота 0x1e), лечение **встаёт на «платном» HP**:
  юнит доходит до значения HP, кратного 4, и дальше не лечится, пока не поест;
- звери, растения и здания через `0x18ab2` лечатся **бесплатно** (тип ≥ 14);
- баг с маной срабатывает только при `al > 1` (MANA < MAG и MANA+al > MAG), т.е. при `al = 1`
  недостижим; воспроизводить всё равно надо — `al` приходит и из других мест.

Здания лечатся не здесь, а отдельной веткой «самопочинка» (§7.4).

## 5. Заказ производства: поля и машина состояний (`0x186b3`)

Одно здание — **один заказ**, очереди нет. Поля записи здания:

| поле | смысл |
|---|---|
| `+0x09` (u8) | сколько шагов надо сделать (`COST_STEPS`) |
| `+0x0a` (u8) | сколько шагов сделано |
| `+0x1b` (u32) | сколько еды уже уплачено |
| `+0x1f` (u32) | еда за один шаг (`COST_FOOD`) |
| `+0x33` (u32) | индекс пункта меню (он же «что производим») |
| `+0x23` (u32) | указатель на «гостя» — запись погибшего юнита, которую надо переиспользовать |
| `+0x50` (u8) | флаги: **1** = идёт производство, **2** = здание строится, **4** = пауза «нет еды» |
| `+0x51` (u8) | прогресс стройки (для флага 2) |

Полный шаг здания:

```
buildingStep(b):
  if ORDER != 0xff:                       # отложенный приказ применяется тут же
      STATE = ORDER; TARGET = [+0x47]; ORDER = 0xff; [+0x23] = 0

  hi = STATE >> 4
  if hi == 6:  return death(b)            # §9.3
  if hi == 7:  return order(b)            # см. ниже

  f50 = [+0x50]
  if f50 != 0 and (f50 & 4) == 0:
      if f50 & 1:                                     # ---- производство
          per = [+0x1f]
          if food[owner] < per:  return pause(b)      # нет еды -> флаг 4, STATE = 0
          food[owner] -= per
          [+0x1b] += per
          [+0x0a] += 1
          if [+0x09] > [+0x0a]:  return repair(b)     # ещё не готово; ремонт идёт параллельно
          [+0x50] = 0
          return spawn(b)                             # §7
      if f50 & 2:                                     # ---- стройка
          HP += 1;  [+0x51] += 1
          if [+0x51] >= HPMAX:  [+0x50] = 0           # достроено
          return
  return repair(b)

order(b):                                 # STATE 0x7f / 0x7e
  if STATE == 0x7f:
      if [+0x50] & 4:                     # стояли на паузе -> снять паузу
          [+0x50] &= ~4;  STATE = 0;  return
      idx = TARGET & 0x1f
      [+0x0a] = 0
      [+0x09] = COST_STEPS[type−26][idx]
      [+0x1f] = COST_FOOD [type−26][idx]
      [+0x1b] = 0;  STATE = 0;  [+0x50] = 1
      return
  if STATE == 0x7e:
      if ([+0x50] & 4) == 0:  return pause(b)         # первый 0x7e = ПАУЗА
      [+0x50] &= 0xfa;  STATE = 0                     # второй = отмена
      food[owner] += [+0x1b]                          # возврат уплаченного
      return
  STATE = 0                                # любое другое 0x7x — просто сброс

pause(b):  [+0x50] |= 4;  STATE = 0        # + сообщение в панели, если здание выделено
repair(b): if (0x31b66 == 0) and HP < HPMAX: HP += 1
```

Важные следствия (все проверены на эталоне):

1. **Оплата идёт каждый игровой шаг, а не «раз в 16 кадров»**: заказ на 250 шагов по 20 еды
   списывает ровно 20 еды каждый шаг в течение 250 шагов. Полная цена = `steps × food_per_step`
   (см. §6), время = `steps` шагов = `steps / 18.2` секунд.
2. **Спавн происходит на шаге `steps`**, т.е. сразу после последнего платежа, в том же вызове.
3. **Пауза «нет еды» не отменяет заказ**: `[+0x1b]` (уплаченное) сохраняется, `[+0x0a]` тоже.
   Повторный приказ 0x7f **не переоформляет** заказ, а только снимает паузу — производство
   продолжается с того же места.
4. **0x7e — двухступенчатый**: при работающем заказе он ставит паузу (тот же путь, что и «нет еды»),
   и только повторный 0x7e отменяет заказ с полным возвратом уплаченного.
5. Ремонт (+1 HP раз в 16 шагов) идёт **параллельно** производству, но не в тот шаг, когда происходит
   спавн, и не во время стройки.

## 6. Что какое здание производит и почём

Две таблицы, по 32 записи на здание (индекс `(type − 26)·32 + menuIdx`):
`COST_FOOD = u32[0x30eac]` (еды за шаг) и `COST_STEPS = u8[0x315ac]` (шагов).
Число реально доступных кнопок меню — `u32[0x4273c + (type−26)·8]`
(у Sanctuary в коде отрисовки `0x26a5d` рисуются 2 + 13 = **15** кнопок, таблица даёт 13).

слотов одинакова (`0x7fff / 0x7 / 0x3fff / 0xf / …`), т.е. **племя набор построек не ограничивает**.

## 7. Спавн: что происходит по окончании заказа

Диспетчер по типу здания (порядок = `type − 26`):
`0x1d36f` Sanctuary, `0x1d4df` Barracks, `0x1d673` Armory×2, `0x1d691` Food-storage,
`0x1d6f4` Elf, `0x1d745` Wizard, `0x1d796` Warlock, `0x1d7e7` Ranger,
`0x1d838`/`0x1d889`/`0x1d8da`/`0x1d92b`/`0x1d97c` — динозавровые дома 9..13.

### 7.1 Точка появления
Юниты появляются в точке `(X_здания, Y_здания + 64)`, предмет из арсенала — в `(X, Y + 96)`,
кучка еды со склада — в `(X, Y + 64)`. Дальше `0x1ccdd` (юниты) или `0x1ce37` (предметы) ищут
ближайший свободный тайл расширяющимися квадратами 1×1, 3×3, 5×5 … от этой точки.

### 7.2 Создание юнита (`0x1caf0`)
Берётся запись из свободного списка, заполняются статы из таблицы §3, `SKILLS(+0x17) = 0x3f`,
инвентарь обнуляется, `+0x21 = 0x1e` (пустой слот еды), `DIR = rand(8) + 1`, `ORDER = 0x3f`,
прямоугольник «домашней зоны» `+0x55..+0x58` = тайл ± 3 с обрезкой по краям карты (§13.2).

### 7.3 Реинкарнация «гостя»
Если `[+0x23]` здания не 0 (ИИ передал запись погибшего юнита), новая запись **не выделяется**:
переиспользуется старая, статы сбрасываются по таблице, юнит выпускается из здания и получает
приказ идти в случайную точку своего прямоугольника `+0x55..+0x58`.
Особенность оригинала: в этом пути `MAG` берётся из байта `+2` таблицы (MANA), а не из `+1`
(на видимом результате не сказывается — в таблице §3 байты `+1` и `+2` у всех типов равны).

### 7.4 Самопочинка зданий
Любое здание без активного заказа и без стройки получает **+1 HP раз в 16 шагов**
(тот же «медленный тик» `0x31b66 == 0`), пока HP < HPMAX. Полное восстановление Sanctuary
с 1 HP — 254 × 16 = 4064 шага ≈ 223 с.

## 8. Строительство

### 8.1 Футпринт зданий (`0x3176c` количество, `0x31770` указатель на список)
Список — пары `i32` (dx, dy) **в пикселях** относительно левого верхнего тайла здания:

| здания | клеток | смещения (px) | размер |
|---|---:|---|---|
| 26 Sanctuary, 28 Armory, 29 Armory | **6** | (0,0) (32,0) (0,32) (32,32) (64,0) (64,32) | 3×2 тайла (96×64 px) |
| 27, 30, 31…39 (все остальные) | **4** | (0,0) (32,0) (0,32) (32,32) | 2×2 тайла (64×64 px) |

Здание растёт **вправо и вниз** от своей точки привязки. Спрайты (`0x303b6`/`0x303b8`) совпадают:
96×64 у трёхклеточных, 64×64 у остальных.

### 8.2 Штамповка в сетке BI
- поставить (`0x1dac2`): для каждой клетки футпринта `BI[cell] = (BI[cell] & 3) | ((owner+1) << 2)`;
- снять (`0x1db19`): `BI[cell] &= 3` (остаются только биты «разведано» и «лежит предмет»).

### 8.3 Проверка места (`0x1ce81`, `0x1cd2d`)
Клетка годна, если: она внутри `mapW × mapH`; `BG[cell] & 0xf800 == 0`; байт свойств тайла
`0x3183c[BG[cell] & 0x7ff]` имеет бит 0; `BI[cell] & 0xfc == 0` (никто не занимает).
`0x1cd2d` ищет расширяющимися квадратами позицию, где годны **все** клетки футпринта, и возвращает её.
Если найденная точка не совпала с текущей, конструктор сначала идёт туда (`0x19f43`), и только
дойдя — превращается.

### 8.4 Превращение конструктора в здание (`0x1d1cf`)
Срабатывает, когда конструктор (тип 4) с `ANIM (+0x4f) == 1` **прибывает** в целевую точку:
```
K   = [+0x59]                       # вид здания из меню Sanctuary
TYPE = K + 26 ;  STATE = 0
[+0x50] = 2                          # флаг «строится»
HPMAX = stats[TYPE].hpmax ;  HP = 0 ;  [+0x51] = 0
MAG = MANA = stats[TYPE].mana ;  ATK/DEF/SPD = stats[TYPE]
проштамповать футпринт в BI (0x1dac2)
для каждого из 12 слотов инвентаря: если не пуст — выложить предмет на землю в (X, Y);
    для слота с едой (0x1e) количество кучки = FOOD (+0x13);  слот обнуляется
если TYPE == 30 (склад):  g_nStorage[owner] += 1
```
Дальше каждый шаг: `HP += 1`, `[+0x51] += 1`, пока `[+0x51] < HPMAX`; затем `[+0x50] = 0`.
**Время стройки в шагах = HPMAX здания** (Sanctuary 255, Food-storage 160, Barracks 200 …),
т.е. 8.8…14 с. Готовое здание сразу с полным HP.

Обратите внимание: поле `FOOD` конструктора при этом **не обнуляется** — см. §14.4.

## 9. Склад (Food-storage, тип 30)

### 9.1 Сдача еды носильщиком
См. §11.2. Ключевые числа: прямоугольник «дошёл» = `X ∈ [Xскл−32, Xскл+64]`,
`Y ∈ [Yскл−32, Yскл+64]`; за **один шаг** отдаётся `FOOD − 50` (если `FOOD > 50`) или всё `FOOD`
(если `FOOD ≤ 50`); еда зачисляется **владельцу склада**.

### 9.2 Выдача (`0x1d691`)
```
if food[owner] == 0:  ничего (только звук)
создать на земле у (X, Y+64) кучку типа 0x1e
amount = min(WITHDRAW[idx], food[owner])      # WITHDRAW = [10, 100, 1000, 10000]
food[owner] -= amount
количество кучки = amount & 0xffff
```
Заметьте: кучка создаётся **до** проверки количества и с количеством 1, потом перезаписывается;
при `amount ≥ 65536` количество обрежется по модулю 65536.

### 9.3 Гибель склада (`0x1886e`)
При переходе `STATE 0x6f → 0x60`:
```
share = food[owner] / (g_nStorage[owner] + 1)     # целочисленно
food[owner]      -= share
g_nStorage[owner] -= 1
if share >= 0x10000: share = 0xffff
while share >= 50:                                 # рассыпать кучками, каждая вдвое меньше
    точка = (X + rand(64) по Y, X по X) -> ближайший свободный тайл (0x1ce37)
    создать кучку 0x1e с количеством share
    share >>= 1
```
То есть **сгорает не share, а share минус то, что легло кучками**; сумма кучек
`share + share/2 + share/4 + … ≈ 2·share`, но каждая кучка — отдельный предмет, который ещё надо
собрать. Проверено на трассе `long_m9_t3`: 10000 → 6667 (делитель 3) → 3334 (делитель 2).

Прочие здания при гибели ставят таймер 0x64 «гостю» (`[+0x23]`), если тот есть и владелец не человек.

### 9.4 Захват (`0x1d9cd`)
Конструктор с `+0x59 == 14` (0x0e), дошедший до чужого здания:
```
если здание — склад (30):
    share = food[старый] / g_nStorage[старый]      # ДЕЛИТЕЛЬ БЕЗ +1, в отличие от гибели
    food[старый] -= share ;  g_nStorage[старый] -= 1
    food[новый]  += share ;  g_nStorage[новый]  += 1
владелец здания = владелец конструктора
если здание что-то производило: снять флаги 1 и 2 (не 4!), «гостю» сбросить таймер
перештамповать футпринт в BI новым владельцем
конструктор исчезает (0x1aaf7)
```

## 11. Состояния 0x4x (добыча) и 0x5x (перенос)

### 11.1 Добыча / охота — состояния 0x4x (`0x1918c`)

Биты младшего ниббла: **4** = «начать движение», **2** = «еду», **1** = «подбираю»,
**8** = «после подбора вернуться в 0x3f, а не в 0x37».

```
takeStep(u):
  st = STATE
  if st & 4:                       # 0x44/0x4c — старт
      STATE = (st & ~4) | 2        # -> 0x42 / 0x4a
      return startMove(u)          # 0x1db94
  if st & 1:                       # 0x41/0x49 — стоим на клетке с предметами
      подобрать всё с текущего тайла (0x1c409)
      если что-то подобрали:
          если TYPE < 4:  переэкипировать оружие (0x1c791) и щит (0x1c8ec)
          если TYPE >= 14: ORDER = 0x3f; return            # звери просто едят
          если FOOD >= ((HPMAX << 6) & 0xffff):            # ПЕРЕГРУЗ
              return carryToStorage(u)                     # 0x17361
      ORDER = (STATE & 8) ? 0x3f : 0x37
      return
  # 0x42 — едем
  если шаг движения вернул «прибыл»:  STATE = (STATE & ~2) | 1
```

**Порог перегруза = `HPMAX · 64`** (для Commoner HPMAX 30 → 1920, для Muscle-man 70 → 4480,
для Velociraptor 80 → 5120). Пока ноша меньше порога, юнит продолжает собирать; при достижении —
идёт на ближайший склад.

`carryToStorage` (`0x17361`):
```
склад = ближайший свой Food-storage по чебышёвской метрике в пикселях (0x23da0)
если склада нет — ничего (юнит остаётся с ношей)
слот = первый из 6..8 со значением 0x1e
ORDER = 0x51 + слот ;  [+0x47] = склад ;  [+0x4b], [+0x4d] = X, Y склада
```
`0x23da0` перебирает весь список юнитов, берёт живые записи типа 30 того же владельца и минимизирует
`max(|dX|, |dY|)` в 16-битной арифметике.

### 11.2 Перенос — состояния 0x50 и 0x51+n (`0x19229`)

`0x51 + n` означает «использовать слот инвентаря n»; при первом же вызове состояние нормализуется:
`[+0x51] = STATE − 0x51; STATE = 0x50`.

```
carryStep(u):
  if STATE != 0x50:
      [+0x51] = STATE − 0x51 ;  STATE = 0x50
      if !reached(u):  return startMove(u)
  else:
      arrived = (X & 31 == 0 && Y & 31 == 0) && reached(u)
      if !arrived:
          если шаг движения не вернул «прибыл»: return
          if !reached(u):  ORDER = 0x3f;  return

  n = [+0x51]
  if INV[n] == 0:  ORDER = 0x3f;  return          # нечего нести
  T = [+0x33] (цель)

  # --- А. цели нет: выложить на землю
  if T == 0:
      взять свободную запись предмета; если нет — ORDER = 0x3f, return
      если INV[n] == 0x1e:  ax = FOOD; если ax != 1: ax >>= 1;  списать ax; тип = 0x1e, кол-во = ax
      иначе:                снять с руки, если надет; тип = INV[n]; INV[n] = 0; кол-во = 1
      положить на тайл юнита;  ORDER = 0x3f;  return

  # --- Б. цель — склад (30)
  if TYPE(T) == 0x1e:
      give = FOOD;  если give > 50: give -= 50
      food[owner(T)] += give
      FOOD -= give
      если FOOD == 0: INV[n] = 0
      ORDER = 0x37;  return

  # --- В. цель — арсенал (28/29): продать предмет
  if TYPE(T) in (0x1c, 0x1d):
      b = INV[n]
      если b >= 0x0f:  ORDER = 0x3f; return                  # артефакты не продаются
      INV[n] = 0
      ax = ((COST_FOOD[армори][b] & 0xff) × COST_STEPS[армори][b]) & 0xffff
      добавить (ax >> 1) еды юниту
      ORDER = 0x37;  return

  # --- Г. цель — другое здание: ничего
  if TYPE(T) >= 0x1a:  ORDER = 0x3f;  return

  # --- Д. цель — юнит: передать предмет (еду — половину)
  положить предмет на землю, тут же дать цели подобрать его (0x1c470);
  если не влез — вернуть на место и ORDER = 0x3f;
  иначе снять предмет/еду у себя (для еды — та же «половина», что в А), ORDER = 0x3f
```

**«Дошли» (`0x1954f`)**:
- цели нет → «дошли» ⟺ `X == DSTX && Y == DSTY`;
- цель мертва (`+0x5b & 1` или STATE 0x60) → ORDER = 0x3f, считается «дошли»;
- цель — **юнит** (тип < 26) → `|X−Xц| ≤ 32` **и** `|Y−Yц| ≤ 32` (по 16-битному модулю);
- цель — **склад** (30) → `Xц−32 ≤ X ≤ Xц+64` и `Yц−32 ≤ Y ≤ Yц+64` (прямоугольник 3×2 тайла);
- цель — **арсенал** (28/29) → `Xц−32 ≤ X ≤ Xц+96` и `Yц−32 ≤ Y ≤ Yц+64` (4×2 тайла);
- цель — иное здание → ORDER = 0x3f, «не дошли».

> Прямоугольники не совпадают с футпринтами: склад занимает 2×2 тайла, а «зона сдачи» у него 3×2;
> арсенал занимает 3×2, а зона — 4×2. Слева и сверху зона всегда на один тайл шире здания.

### 11.3 Подбор предметов с тайла (`0x1c409`, `0x1c470`)

```
pickAll(u):
  n = 0
  для каждого предмета в списке, чей тайл == тайлу юнита:
      если удалось положить в инвентарь: n++
  вернуть «успех», если n >= 1

put(item, u):
  если тип == 0x1e (еда):
      слот = первый из 6..8 со значением 0x1e, иначе первый пустой; нет — ОТКАЗ
      добавить количество к FOOD (0x1c679)
      если что-то не влезло (FOOD упёрлось в 0xffff): количество предмета = остаток + 1, предмет ОСТАЁТСЯ
      иначе: пометить слот 0x1e, снять бит 1 в BI, вернуть запись предмета в свободный список
  иначе:
      база = флаги&2 ? 0 : флаги&4 ? 3 : флаги&0x10 ? 9 : 6
      слот = первый пустой из [база, база+3); нет — ОТКАЗ
      положить, снять бит 1 в BI, освободить запись
```

Выбор оружия (`0x1c791`) и щита (`0x1c8ec`) после подбора вызывается **только для типов 1..3**.
Внутри: если рука пуста (`+0x15`/`+0x16` == 0xff) — берётся предмет из соответствующей группы слотов
у **любого** владельца; если что-то уже надето, юниты человека-игрока **не** переэкипируются
(у него это ручная операция), а у ИИ — переэкипируются на предмет более высокого класса.
Стрелковое оружие (id 5..7 — Poison-Arrow, Fire-Arrow, Arrow) при надевании снимает щит
(`+0x16 = 0xff`) и не даёт его надеть заново, пока оно в руке.

## 12. Предметы на земле (пул OI)

- Пул: **500 записей по 16 байт** от `0xf4f34` (регион OI, 8000 байт; в файлах карт — секция OI).
- Запись: `+0` тип (id предмета, 0x1e = еда), `+1` тайл X, `+2` тайл Y, `+4` таймер (u16),
  `+6` количество (u16), `+8` prev (u32), `+12` next (u32).
- Указатели — **байтовые смещения внутри пула**, 0 = «нет». Голова живого списка `0x31b7c`,
  голова свободного списка `0x31b80`. Запись со смещением 0 фактически не используется
  (0 = признак конца списка).
- При выкладывании (`0x1c5a8`) таймер ставится в **0x19 = 25**, а в сетке BI на тайле поднимается
  **бит 1** («здесь что-то лежит»).
- Раз в шаг фаза `0x1c340` пробегает список и заново поднимает бит 1 у всех занятых тайлов
  (нужна, потому что бит могли затереть другие подсистемы).

### 12.1 Гниение (`0x1c370`)
Вызывается из ИИ-диспетчера, когда `(номер шага & 0x7f) == 0` — то есть **раз в 128 шагов** (≈7 с):

```
для каждой записи в живом списке:
  если тип == 0x1e (еда):
      количество -= 1 (по модулю 65536)
      если количество == 0 -> удалить
  иначе если тип < 0x0f (обычные предметы 1..14):
      таймер -= 1
      если таймер == 0:
          количество -= 1
          если количество == 0 -> удалить
  # тип >= 0x0f (артефакты) не гниют вообще
удаление: снять бит 1 в BI, вернуть запись в свободный список
```

Числа:
- **обычный предмет живёт 25 × 128 = 3200 шагов ≈ 176 с**, потом исчезает;
- **артефакты лежат вечно**;
- **кучка еды теряет 1 единицу за 128 шагов** — то есть туша T-Rex’а (1000 еды) полностью
  сгниёт только за 128 000 шагов (≈ 2 часа). Практически еда не портится, а вот кучка из 1–2 единиц
  исчезает за 1–2 «тика».

> **Ловушка:** кучка с количеством **0** не удаляется, а превращается в кучку на **65535** еды
> (0 − 1 = 0xffff ≠ 0). Такая кучка появляется, если конструктор с `FOOD = 0` превращается в здание
> (§8.4) — единственный найденный путь. См. §14.5.

### 12.2 Труп как источник еды (`0x19693`, ветка 0x6f → 0x60)
При смерти любого юнита:
```
STATE = 0x60 (труп), ATKCTR = 0, снять отпечаток с сетки
для всех 12 слотов инвентаря: выложить предмет на землю (в тайл +0x53);
    для слота с едой количество кучки = FOOD (+0x13) целиком
для типов 14..23 (дикие звери): счётчик убитых 0x33358[тип] += 1
```
Труп лежит **192 шага** (`+0x2c` растёт до 0xc0 ≈ 10.5 с), затем запись уходит в свободный список
(или, для владельцев под ИИ, остаётся с флагом «мёртв» ради респавна, §13.3).

Именно это и есть охота: убил Tyrannosaurus’а — на его тайле появилась кучка «Foods» на 1000 единиц.

## 13. Дикая природа и растения

### 13.1 Кто такие дикие
Типы 14..23, владелец 8 («природа»). У них FOOD = мясо (§3), они не платят за лечение
и не строят. Обработчик — `0x184c8`.

### 13.2 Прямоугольник выпаса `+0x55..+0x58`
Ставится при создании юнита (`0x1caf0`) от тайла появления:
```
+0x55 = max(tileX − 3, 0)        +0x57 = min(tileX + 3, mapW)
+0x56 = max(tileY − 3, 0)        +0x58 = min(tileY + 3, mapH)
```
То есть окно **7×7 тайлов** вокруг точки рождения (с обрезкой по краям карты).
Точка рождения запоминается отдельно в `+0x59/+0x5a`.

### 13.3 Решение зверя (`0x172c5`)
Вызывается на каждом шаге, когда зверь стоит ровно на тайле, но срабатывает не всегда:
счётчик `+0x50` растёт на 1 каждый цикл «простоя» (состояние 0x38: `ATKCTR` тикает вниз
от `rand(20) + 5`, т.е. 5..24 шага на цикл), а сработать может лишь при `+0x50 >= 14`.
Итого решение принимается примерно раз в 14 × 14.5 ≈ **200 шагов ≈ 11 с**.

```
если +0x50 < 14: выход
если (STATE & 0xf0) != 0x40:                       # не занят подбором
    предмет = ближайший подбираемый предмет в радиусе обзора (0x170f6)
    если нашёлся:  ORDER = 0x44 (идти брать), точка = тайл предмета
    иначе:         цель = случайный тайл внутри (+0x55..+0x58):
                       ty = +0x56 + rand(+0x58 − +0x56)
                       tx = +0x55 + rand(+0x57 − +0x55)
                   если тайл проходим (0x1e609) — приказ идти туда (0x19fbf)
+0x50 = 0
```

Что зверь считает «подбираемым», решает маска `0x171d3`: бит 0x10 — есть свободный слот под еду
(6..8), биты 1/2/4/8 — свободны слоты оружия/щита/артефакта/расходника.
Поэтому травоядные и хищники одинаково подбирают с земли еду и оружие.

### 13.4 Респавн (`0x18058` → `0x1cfcb`)
Мёртвая запись (`+0x5b & 1`) владельца 8 или владельца под ИИ каждый шаг увеличивает `+0x4f`;
когда `+0x4f >= T_TYPE_TIMER[type] + счётчик_убитых`, зверь возрождается на своей точке рождения
`+0x59/+0x5a` с полными статами и приказом идти в случайную точку прямоугольника выпаса.

`T_TYPE_TIMER = u16[0x36d82 + type·2]` (в шагах):

| тип | таймер | тип | таймер | тип | таймер |
|---|---:|---|---:|---|---:|
| 1 Commoner | 360 | 9..13 ручные дино | 1080 | 19 Mammoth | 8100 |
| 2 Muscle-man | 540 | 14 Tyrannosaurus | 6480 | 20 Musso | 2880 |
| 3 Warrior | 540 | 15 Brachiosaurus | 5400 | 21 Tiger | 1800 |
| 4 Constructor | 720 | 16 Centrosaurus | 5400 | 22 Leopard | 1080 |
| 5..8 маги | 540 | 17 Stauricosaurus | 5400 | 23 Cur | 720 |
| 26,27,30 здания | 540 | 18 Daemon | 5400 | 24 Nexious Weed | 4500 |
| 28,29,31..39 здания | 1080 | | | 25 Poisonous Mushroom | 7200 |

Дополнительное слагаемое `0x33358[type]` (число уже убитых зверей этого типа) делает каждый
следующий респавн длиннее предыдущего: убил 5 тигров — шестой возродится через 1800 + 5 шагов…
(счётчик прибавляется в шагах, поэтому эффект слабый, но он есть).

### 13.5 Растения (`0x18568`, `0x1d12e`)
Типы 24/25 (Nexious Weed, Poisonous Mushroom, владелец 8) — стационарные, атакуют соседей
(радиус 4 и 3 клетки соответственно), лечатся через `0x18ab2` раз в 16 шагов бесплатно.
После гибели отрастают на месте по тому же таймеру `T_TYPE_TIMER` (4500 / 7200 шагов ≈ 4 / 6.6 мин).
С точки зрения экономики: растение — источник еды (FOOD 30/20) для того, кто его убьёт.

## 14. Странности оригинала, которые надо повторить

1. **Оплата производства идёт каждый шаг, а не раз в 16 кадров.** Ранние заметки утверждали
   обратное; трасса `long_m5_t0` показывает −10 еды на каждом из 110 подряд идущих шагов.
2. **Асимметрия цен арсенала.** Производство индексирует таблицу по номеру кнопки, а продажа
   приказом — по id предмета, при том что `id = idx + 1`. В результате «половина цены» для Sword
   считается по строке Spear: 165 вместо ожидаемых 175. Плюс продажа считается **8-битным
   умножением** (`(COST_FOOD & 0xff) × COST_STEPS`), что при еде за шаг ≥ 256 дало бы мусор
   (в арсенале всегда 5, так что практически безопасно).
3. **Iron-Shield стоит 2 еды** в панели юнита (поле цены в таблице предметов), при том что
   Wood-Shield — 40, а Wather-Shield — 600. Похоже на опечатку в данных, но воспроизводить надо.
4. **Конструктор, ставший зданием, дублирует свою еду**: кучка на земле получает количество,
   равное `FOOD` конструктора, а поле `FOOD` записи (уже здания) **не обнуляется**. Это влияет
   на условие победы миссии 1 («собрать 3000 еды» — сумма FOOD по всем живым записям игрока,
   включая здания, `0x17989`).
5. **Кучка еды с количеством 0 превращается в кучку на 65535** при первом же «тике гниения»
   (§12.1). Достижимо, если строить зданием конструктора с пустым `FOOD`.
6. **Покупка предмета в панели юнита списывает всю ношу еды, а не цену.** `0x1763c` сравнивает
   цену с `FOOD` только как проверку «хватает ли», а списывает `FOOD` целиком.
7. **ИИ считает цену и выбирает пункт меню по типу юнита, а не по номеру кнопки.** `0x1ced8`
   пишет `TARGET = тип погибшего юнита` и считает цену как
   `u8[0x30eac + (дом−26)·128 + тип·4] × u8[0x315ac + (дом−26)·32 + тип]` (оба чтения **8-битные**).
   Практические последствия: заказав «замену» Commoner (тип 1), казарма делает
   **Muscle-man** (пункт 1) за 1200 вместо Commoner’а за 500; заказав замену Warrior (тип 3) —
   Constructor’а (пункт 3) за 800. Для домов тренировки индекс уходит за пределы видимого меню
   и берёт «запасные» строки таблицы (Elf по пункту 5 = 1100), а пакет бонусов читается
   за границей своей таблицы (Elf по пункту 5 попадает в таблицу Wizard). Подробности —
   зона ответственности ИИ, здесь важно, что таблицы цен читаются именно так.
8. **`0x7e` — не «отмена», а «пауза»**, и только повторный `0x7e` при уже стоящей паузе отменяет
   заказ с возвратом. Симметрично `0x7f` при паузе не переоформляет заказ, а снимает паузу.
9. **Гибель склада и захват склада делят еду по-разному**: гибель — на `nStorage + 1`,
   захват — на `nStorage`. При `nStorage == 0` захват отдаёт 0 (защита от деления на ноль есть).
10. **Носильщик оставляет себе 50 еды**, но только если несёт больше 50; при `FOOD ≤ 50` отдаёт всё.
    Отдаёт **владельцу склада**, а не своему: код берёт `owner` из записи цели.
11. **Зоны «дошёл до здания» шире футпринта** и несимметричны (§11.2): всегда на тайл шире слева
    и сверху.
12. **Регенерация видит HP уже после урона, полученного в этом же шаге** от юнитов, стоящих раньше
    в списке. Отравленный растением юнит поэтому «через раз» платит еду: цепочка
    HP 29 → (яд) 28 → (лечение, 28 % 4 == 0, −1 еда) 29 наблюдается в трассах буквально.

## 15. Как это проверено

`tools/spec_check_economy.py` — **независимая** реализация формул этого документа на Python
(порт `js/port/economy.js` не импортируется; из образа читаются только таблицы). Два режима,
итог общего прогона `python3 tools/spec_check_economy.py --all`:

```
еда игроков         126064 / 126064
поля зданий        3298998 / 3298998
регенерация/еда       3532 / 3532
гниение предметов      251 / 251
итоговые числа          55 / 55
ВЕРДИКТ: 3 428 900 сверок, расхождений 0 — ОК
```

### 15.1 Трассы эталона (`tools/spec_check_economy.py [путь...]`)
Берётся состояние на шаге k, применяются формулы §4/§5/§7.4/§8.4/§9/§11.2, результат сравнивается
с шагом k+1. Сверяются: еда всех 8 игроков, поля зданий `+0x09/+0x0a/+0x1b/+0x1f/+0x50/+0x51`,
HP и STATE зданий, HP и FOOD людей/ручных динозавров в «медленный тик».

```
long_m1_t1   еда  23992/23992   здания   18620/18620    регенерация    0/0
long_m2_t0   еда  23992/23992   здания  263912/263912   регенерация  105/105
long_m5_t0   еда  15992/15992   здания  383793/383793   регенерация  479/479   (110 шагов производства)
long_m9_t3   еда  15992/15992   здания  427713/427713   регенерация  284/284
m0_t0, m0_t0_orders, m1_t1, m2_t0, m3_t5, m5_t0, m9_t3 — все 0 расхождений
ИТОГО по трассам: 1 401 420 сверок, расхождений 0
```

Не сравниваются (и посчитаны отдельно): шаги, где здание/юнит получил урон в бою — там HP пишет
боевая подсистема; шаг, на котором ИИ вписал заказ `0x7f` прямо в `[+0x2b]` посреди того же шага
(за все трассы такой случай ровно один — дом тренировки в `long_m5_t0`).

### 15.2 Сценарии на эталоне под unicorn (`--scenarios`)
Трассы почти не содержат производства (только один заказ ИИ) и вовсе не содержат состояний 0x5x
(в них встречаются лишь 0x41/0x42), поэтому эти ветки проверяются прямыми сценариями: эталон
поднимается под unicorn, ИИ выключается (`0x32aec[слот] = 0`), заказ вписывается в память,
дальше пошагово сверяется та же модель. Покрыто:

| сценарий | что проверено |
|---|---|
| производство, миссия 9 (и 8 для Velociraptor tr.) | Sanctuary, Barracks, Armory, Food-storage, Elf tr., Triceratops tr., Diloposaurus tr., Velociraptor tr. — до 4 пунктов меню каждый, 3537 шагов оплаты; отдельно сверена итоговая сумма `steps × food_per_step` |
| пауза/отмена | «нет еды» → пауза; `0x7f` снимает паузу и производство идёт дальше; `0x7e` при работе = пауза; второй `0x7e` = отмена с возвратом ровно уплаченного |
| выдача склада | все 4 пункта (10/100/1000/10000), кучка на земле с тем же количеством, и вариант «еды меньше, чем в таблице» |
| сдача еды на склад | ноша 1 / 30 / 50 / 51 / 1000 → отдано `FOOD − 50` или всё; слот 0x1e очищается ровно тогда, когда `FOOD` стал 0 |
| продажа в арсенале | предметы 1, 2, 8, 14 → в ношу зачислено `((COST_FOOD[армори][id] & 0xff) × COST_STEPS[армори][id]) >> 1` |
| постройка | Sanctuary idx 4 выдал Constructor'а с `+0x59 = 4`; превращение в Food-storage: TYPE, `+0x50 = 2`, HP = 0, HPMAX из таблицы, `g_nStorage++`, кучка еды с количеством = FOOD конструктора; затем 160 шагов прогресса по +1 HP и снятие флага |
| гниение | 25 «тиков» по 128 шагов, 251 сверка записей пула (еда и обычные предметы) |

### 15.3 Что не удалось покрыть эмпирически
- **Гибель склада** проверена только по трассе `long_m9_t3` (два случая: делители 3 и 2);
  раскладка остатка кучками (`while share >= 50`) на трассах не наблюдалась — формула взята
  из порта и дизассемблера.
- **Захват здания конструктором** (`0x1d9cd`) в трассах не встречается; сценарий не сделан,
  потому что требует конструктора с `+0x59 = 14` и чужого здания рядом.
- **Панельная покупка/продажа предметов** (`0x1763c`/`0x175e8`) вызывается из маршрута
  «автоторговля у арсенала» (`0x173a3`), прямых вызовов которого в образе не нашлось —
  вероятно, вход через таблицу. Числа взяты из дизассемблера, поведением не подтверждены
  (включая баг §14.6).
- **Передача предмета другому юниту** (ветка Д в §11.2) в трассах не встречается.
- **Кучка еды с количеством 0 → 65535** (§12.1) выведена из формулы гниения, отдельным сценарием
  не воспроизводилась.
