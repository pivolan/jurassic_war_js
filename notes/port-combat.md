## Замечания
- Интеграция: `compare.mjs` — m0_t0 200/200, m0_t0_orders 200/200, m1_t1 300/300, m2_t0 300/300 (после правки: в 0x1a7cb тип юнита перечитывается после удара, т.к. убийство превращает Commoner в Warrior и кадр берётся уже по новому типу).
- Дублирование портов другими темами (их версии загружаются позже и перекрывают мои): 0x1ff1c, 0x1ffb6, 0x1ffeb (economy/magic), 0x1aaf7, 0x1a65d (economy), 0x19fbf (magic). Claims были мои; расхождений в тестах не видно.
- Причуды оригинала, воспроизведены: 0x1ad3c читает тип по индексу СНАРЯДА как по индексу юнита (`[esi+0xe4404]`, esi = снаряд); 0x1f20f сравнивает сумму статов зверя только с потолком SPD (`mov bx` вместо `add`); в 0x1b2ef координата Y сравнивается с шириной карты, X — с высотой; 0x1aef4 при блокировке щитом создаёт «плевок» 0x1b876 от кастера; 0x1b0de может освободить снаряд дважды (0x1c2ef не обнуляет вид).
- В 0x1b529 регистр al для 0x1c135 равен индексу обработчика (kind−0x80 = 0xe), т.е. фильтр по владельцу фактически не работает.
- fncheck: миссия 16 не грузится в эталоне (смена тайлсета → ошибка загрузчика спрайтов), вне моей темы.

## Не покрыто тестами
- 0x1d9cd (захват здания) — нужен конструктор с приказом 0x0e; 0x18bb3 в состоянии 0x1f с edi=0 (ИИ-поход) встречается редко; 0x1cfcb (респавн через 720+ шагов) проверен только на дампе смерти; UI-ветки 0x1a65d/0x1d9cd (когда юнит выделен) идут через реестр в непортированные функции 0x11c13/0x2673d/0x26a5d/0x2696a/0x2693c/0x2698e/0x291ce.

## Дополнение (по длинным трассам)
- long_m9_t3 (шаг 612, летающие Rhamphorhynchus): в 0x1b529 (молния) продолжение поиска жертв через 0x1c13b шло с границами из регистров; в оригинале 0x1c13b каждый раз пересчитывает прямоугольник из координат снаряда (esi), а edx после ГСЧ значения не имеет. Исправлено в combat.js — передаю пересчитанные границы.
- long_m2_t0 (шаг 2274), long_m5_t0 (1924), long_m1_t1 (367) — состояние 0x11 «подход к цели»: причина в `move.js` 0x1e685 (проходимость тайла): при переходе из ветки «сосед по таблице 0x37910 смотрит на этот тайл» (0x1e6e7 → 0x1e6d3) проверка `test [edx+ebx+MO],0xf` относится к СОСЕДНЕЙ клетке (edx там — смещение из таблицы), а порт проверял исходный тайл; из-за этого симуляция обхода 0x1e1c5 делала лишний шаг и выбирала другую сторону/направление. Исправлено в move.js (согласовано с координатором, функция темы A).
- Итог: long_m1_t1 3000/3000, long_m2_t0 3000/3000, long_m5_t0 2000/2000, long_m9_t3 2000/2000. Кейсы: cases/cmb_* (в т.ч. cmb_m9_l529, cmb_mv_*).
- Заметка по инструментам: хук unicorn, добавленный после прогона, не срабатывает без `mu.ctl_flush_tb()` (кэш трансляции) — учесть в отладочных скриптах.
- Кейс cmb_mv_e685 удалён: расхождение только в старшем байте eax (оригинал оставляет ah от слова тайла), вызывающие используют al/ZF.
